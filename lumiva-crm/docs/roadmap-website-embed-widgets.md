# Бэклог: виджеты сайт ↔ CRM через iframe (кроме текущих веб-форм)

**Статус:** идея на будущее — реализацию начинаем в свободный график, когда будет приоритет.

**Контекст:** сейчас в продукте есть публичные **веб-формы** во `iframe` с дизайном из CRM. Тот же паттерн (публичный маршрут, токен/preview, санитайзер `design`, прозрачный shell для embed) можно повторить для других сценариев.

## Зачем

- Единая точка данных в CRM, без кастомной разработки на стороне сайта.
- Предсказуемая безопасность: allowlist доменов, `frame-ancestors`, ограничения по публичному API.
- Повторное использование инфраструктуры: класс `embed-public-iframe`, отсутствие «серой подложки» CRM в iframe.

## Кандидаты на продукт (по смыслу)

| Направление        | Суть | Примечание |
|--------------------|------|------------|
| Запись / бронь     | Слоты, сотрудник, таймзона → лид/событие в CRM | Высокий спрос в услугах |
| Квиз / многошаг    | Ветвления, квалификация, теги                 | Расширение лид-форм |
| Callback           | «Перезвонить» + очередь / правила             | Часто отдельный виджет |
| NPS / CSAT         | Опрос после сделки или на thank-you          | Мало UI, польза для аналитики |
| Статус обращения   | Read-only по публичному коду (без ЛК)         | B2C без кабинета |
| Каталог с CRM      | Витрина объектов/вакансий из CRM              | Read-heavy, кэш/лимиты |

*Чат, оплата, подпись документов* — тоже возможны, но чаще идут через внешние сервисы; приоритизировать отдельно.

## Технические ориентиры (для оценки)

- Публичный `publicId` + по необходимости **preview**-токен, как у форм.
- Общий **embed layout**: прозрачный `html`/`body`/`#root`, без лишнего UI CRM.
- **Санитайзер** полей `design` и лимиты по числам/строкам на бэкенде.
- **Политика встраивания:** список разрешённых origin для `iframe` (безопасность и злоупотребления).

## Следующий шаг (когда возьмём в работу)

1. Выбрать **один** сценарий (например, бронь или квиз).
2. Согласовать UX: один экран vs многошаг, что пишем в сущности CRM.
3. Спроектировать публичный API (GET конфиг, POST сабмит) по аналогии с embed-forms.
4. Реализация фронта (маршрут `/embed/...` или неймспейс) + бэк.
