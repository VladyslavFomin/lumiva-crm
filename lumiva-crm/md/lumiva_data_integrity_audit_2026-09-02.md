# Lumiva CRM: аудит целостности данных (создание/удаление/назначение) — план и статус

Документ фиксирует находки полного функционального аудита CRUD/assign-логики по всем модулям
(2026-09-02, 7 параллельных фоновых проходов по backend, без RBAC — тот отдельно закрыт
накануне, см. `lumiva_rbac_deep_roadmap.md`) и прогресс их исправления. Полный отчёт с
фильтрами опубликован как артефакт: https://claude.ai/code/artifact/26e2b8ed-1a6c-4e07-b541-4f92d5981b1b

Порядок работы, подтверждённый пользователем: сначала все Critical, затем High, затем Medium,
Low — по решению после.

## 0. Итог аудита

5 Critical, 14 High, 11 Medium, 15 Low. Ничего не фиксилось до согласования списка.

## 1. Critical — статус: ВСЕ 5 ИСПРАВЛЕНЫ И ЗАДЕПЛОЕНЫ (2026-09-02)

- [x] **C1. Удаление канала продаж физически удаляет все продажи по нему.**
      `backend/src/sales-channels/sales-channels.service.ts:177-189`. Убран `saleRepo.delete(...)`,
      остался только `isDeleted=true`. Проверено вживую: продажа переживает удаление канала.
- [x] **C2. AI-сотрудник помечает "реальные" действия исполненными без фактического исполнения.**
      `backend/src/ai-employees/ai-employees.service.ts:774-828` (`createAiAction`). Теперь при
      `!requiresApproval && isRealExecutable(actionType)` вызывается `dispatchRealAction` тем же
      путём, что и в `executeAction` (с откатом в `status:'failed'` при ошибке). Не покрыто живым
      end-to-end тестом (требует реального AI-агента) — проверено только чтением кода, паттерн
      скопирован 1:1 с уже работающего `executeAction`.
- [x] **C3. История лида и дашборд «Активность» — мёртвый код (0 строк в lead_activity).**
      `backend/src/leads/leads.service.ts` (`createForTenant`/`updateForTenant`) теперь вызывают
      `LeadActivityService.add()` при создании/смене статуса/смене ответственного (`await`, не
      fire-and-forget — чтобы не race'ить с остальной логикой). Заодно найден и исправлен
      **дополнительный баг**: `oldStatus` в `updateForTenant` захватывался ПОСЛЕ того как
      `lead.status` уже был перезаписан новым значением — из-за этого `LEAD_STATUS_CHANGED`
      автоматизация никогда не срабатывала вообще (сравнение всегда `dto.status !== dto.status`).
      И ещё один: `dashboard.service.ts`'s `todayMeetingsCount` искал `lead_activity.type='meeting'`
      — такого типа в `LeadActivityType` никогда не существовало; переписан на чтение реальных
      встреч из `Lead.meta.meetings[]` (как это уже делает `calendar.service.ts`). Проверено вживую
      (throwaway-тенант): create → `created`; смена статуса → `status_changed` с верным from/to;
      смена `assignedUserId` → `assignee_changed`.
- [x] **C4. Обработка платёжных вебхуков не атомарна — payment/sale может разойтись навсегда.**
      `backend/src/payments/payments.service.ts` — все три колбэка (iyzico/PayTR/ЮKassa) теперь
      оборачивают `payment.save()` + `markSalePaidIfNeeded()` в один `manager.transaction()`.
      Поведение контроллеров (всегда отвечать 200 даже при ошибке) осознанно не тронуто — это
      отдельный, документированный компромисс против спама ретраями от провайдеров, менять его
      задним числом не входило в этот фикс. Живой тест не делался (нужен реальный подписанный
      вебхук от провайдера) — проверено чтением кода + подтверждено, что TypeORM/Postgres
      поддерживают вложенные транзакции через SAVEPOINT (используется и для C5).
- [x] **C5. Удаление тенанта не затрагивает ~100 таблиц без FK-каскада — orphan-данные навсегда.**
      `backend/src/tenants/tenants.service.ts` (`platformDeleteTenant`). Вместо расширения
      хардкод-списка (который и так уже трижды устаревал по мере роста продукта) — рантайм-
      обнаружение ВСЕХ таблиц с колонкой `tenantId`/`tenant_id` через `information_schema` +
      удаление их строк для тенанта с повторными проходами (каждая попытка в своём `SAVEPOINT`,
      FK-ошибка на одной таблице просто откладывает её на следующий проход, когда её зависимости
      уже опустеют) — самочинящийся порядок, не требует ручного обновления при добавлении новых
      таблиц в будущем. Проверено вживую: throwaway-тенант с посеянными строками в 5 таблицах из
      разных ранее непокрытых модулей (`audit_logs`, `dedup_settings`, `in_app_notifications`,
      `booking_projects`, `booking_locations`) — после `platformDeleteTenant` **0 оставшихся строк**
      ни в одной из ~150 таблиц с tenant-колонкой во всей схеме, сам тенант удалён.

**Как деплоилось**: `docker compose build --no-cache api` + `docker compose up -d api` (нет CI/
staging, стандартный для этого проекта путь). Проверка вживую — через одноразовый throwaway-
тенант (`00000000-0000-4000-8000-000000000099`) и скрипт, вызывающий реальные сервисы через
`NestFactory.createApplicationContext`, не HTTP-моки. Тенант и все его тестовые данные удалены
(последним шагом теста был именно вызов исправленного `platformDeleteTenant`).

- [x] **H3. Кастомные объекты: смена `key` поля молча обнуляла значения существующих записей.**
      `custom-objects.service.ts` `updateField()`: при смене `key` данные мигрируют внутри jsonb
      (`values - oldKey || jsonb_build_object(newKey, values->oldKey)`) тем же вызовом, что сохраняет
      поле. **Найден и исправлен баг в самом фиксе при живой проверке**: Postgres не мог определить
      тип параметра `$2` для `jsonb_build_object` без явного `::text` — без каста запрос падал
      `could not determine data type of parameter $2` при любом реальном переименовании с
      существующими данными. Проверено вживую (после каста): запись с `{old_key:"hello"}` → после
      рескейма поля `old_key→new_key` → `{new_key:"hello"}`, старого ключа нет.
- [x] **H4. Бронирования: переназначение мастера/ресурса обходило проверку конфликта.**
      `reservations.service.ts` `update()`: конфликт теперь проверяется не только при смене
      времени, но и при смене `staffUserId`/`resourceId` без смены времени.
- [x] **H5. Бронирования: массовое переназначение не проверяло конфликты вообще.**

      создают двойную бронь. Ответ эндпоинта и фронтенд (`BookingAvailabilityPage.tsx`) дополнены
      `skippedCount` с отдельным предупреждением (ru/en/tr).
- [x] **H6. Отели: check-in не проверял занятость номера на сервере.**
      `hotel-reservations.service.ts` `checkIn()`: добавлена серверная проверка пересечения дат
      с другими активными бронями на тот же `roomUnitId` (раньше — только фронтенд-дизейбл в
      выпадающем списке, обходился прямым вызовом API или гонкой двух сессий ресепшна).
- [x] **H7. Сотрудники: отдел хранился в двух несинхронных полях.**

- [x] **H8. Сотрудники: жёсткое удаление могло упасть FK-ошибкой / оставить висящие ссылки.**
      `staff-users.service.ts` `deleteForTenant()`: обёрнуто в транзакцию, которая перед удалением
      обнуляет `departments.managerId`, `lead_activity.userId`, `Project.ownerUserId`/`ownerUserIds`
      (raw SQL с `array_remove`, с поправкой на реальное имя колонки `tenant_id` у `crm_projects`) и

- [x] **H9. Проекты/AI: смена владельца через AI рассинхронизировала `ownerUserIds`/`ownerName`.**

- [x] **H14. Биллинг: начисление допкредитов через Stripe можно было задвоить.**

## 3. Medium — статус: ВСЕ 10 ИСПРАВЛЕНЫ И ЗАДЕПЛОЕНЫ (2026-09-02)

(Артефакт указывал 11 в сводном счётчике шапки — при разборе на конкретные находки их 10;
разошлось на единицу в шапке артефакта, не в содержании — реальных 10 находок, все закрыты.)

- [x] **M1. Свой код валюты проекта мог быть длиннее колонки БД — падение при сохранении.**
      `project-currencies.service.ts`'s DTO (`create-project-currency.dto.ts`/
      `update-project-currency.dto.ts`): regex сужен с `{1,8}` до ровно `{3}`. Плюс отдельно —
      `CreateProjectDto.currency` (используется и `UpdateProjectDto` через `PartialType`) вообще
      не имел валидации длины — добавлен `@Length(3,3)`, это и есть реальная точка, где падало
      сохранение самого проекта. Проверено: в проде на момент фикса не было ни одной валюты
      длиннее 3 символов — бэкфилл не требовался.
- [x] **M2. Переименование тега/валюты не обновляло уже созданные проекты.**
      По образцу уже работающего каскада у статусов: `project-currencies.service.ts` — простой
      `UPDATE crm_projects SET currency=... WHERE currency=oldCode`; `project-tags.service.ts` —
      `Project.tags` это `simple-array`, точное совпадение элемента (не substring) сделано в JS
      после выборки проектов тенанта, не текстовым LIKE. Проверено вживую: тег `CRM` в проекте
      → переименован в `CRM-EU` → у проекта тег стал `CRM-EU` (не потерян).
- [x] **M3. Удаление определения кастомного поля не чистило значения в существующих записях.**
      `custom-fields.service.ts` `delete()` и `custom-objects.service.ts` `deleteField()`: после
      удаления определения — `UPDATE <table> SET "customFields"/values = ... - key WHERE ... ? key`
      по всем пяти entity-таблицам (contacts/companies/leads/sales/crm_projects, с поправкой на
      `tenant_id` у последней) и по `custom_object_records`. Проверено вживую на обоих путях.
- [x] **M4. Изменения кастомных полей не попадали в audit log у Контактов/Компаний.**
      `contacts.service.ts`/`companies.service.ts`: `before`-снэпшот теперь включает
      `JSON.stringify(customFields)`, при расхождении в `changes` добавляется запись
      `{field:'customFields'}`. Проверено вживую (с поправкой на то, что `auditLog.log()` —
      fire-and-forget, не await'ится самим сервисом).
- [x] **M5. Движение остатков товара — гонка при параллельных запросах.**
      `products.service.ts` `recordStockMovement()`: атомарный
      `UPDATE product_location_stock SET quantity=GREATEST(0,quantity+delta) ... RETURNING *`
      вместо read-then-write (с обработкой гонки первой вставки строки через перехват `23505`).
      **При живой проверке (20 параллельных +1 к одному товару) обнаружился ВТОРОЙ, более
      глубокий баг вне первоначальной находки аудита**: денормализованная сумма на
      `Product.quantity`/`ProductVariant.quantity` (и `recalcProductQuantity()`) писалась той же
      read-then-write схемой поверх уже исправленного location_stock — 7 из 20 обновлений
      терялись. Исправлено тем же приёмом: сумма пересчитывается подзапросом ВНУТРИ самого
      `UPDATE` (`SET quantity = (SELECT SUM(...) FROM product_location_stock/product_variants ...)`),
      а не литералом, посчитанным в JS. Проверено вживую: последовательно 10-3=7 (верно);
      20 параллельных +1 → итог ровно 27 (было 20 до второго фикса).
- [x] **M6. Сохранение лида из виджета онлайн-чата всегда создавало новый лид.**
      `online-chat.service.ts` `savePublicLead()`: если у сессии уже есть `leadId` — обновляет
      существующий лид (только реально изменившиеся name/phone/email), не создаёт новый; при
      "лид не найден" (удалён) — откатывается на прежнее поведение создания. Проверено вживую:
      два вызова подряд (сначала имя, потом телефон) → один и тот же `lead_id`, телефон обновлён.
- [x] **M7. Получатель рассылки, у которого не получилось отправить, зависал навсегда.**

      `maybeComplete()` не считает такие "исполненными", пока попытки не исчерпаны.

- [x] **M9. Outlook Calendar не сохранял обновлённый refresh-токен.**

      refresh-токен для этого типа гранта, изменение там не требовалось.
- [x] **M10. Смена email сотрудника через общий PATCH могла отвязать деактивацию от входа.**
