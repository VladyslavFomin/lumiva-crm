# Lumiva CRM: глубокий RBAC (поле/действие-уровень + AI-инструменты) — план

Документ фиксирует диагноз текущей жалобы («дал доступ — сотрудник всё равно не видит») и план
дальнейшей работы над правами доступа, разбитый на фазы, чтобы делать по частям, а не одним
гигантским PR. Записан в том же формате, что `lumiva_products_module_roadmap.md`.

## 0. Роль исполнителя

Работаешь как senior full-stack инженер в существующем проекте Lumiva CRM (backend: NestJS +
TypeORM + Postgres, frontend: React + Vite + Tailwind). RBAC уже частично построен — не
изобретай новую систему прав с нуля, расширяй существующую (`backend/src/rbac/*`).

## 1. Что уже есть на момент написания (2026-09-01)

Сегодня в этой же сессии построено и подтверждено живым тестом:

- `RbacGuard` проверяет доступ в порядке: **owner всегда разрешён** → **явный персональный
  override** (`staff_user_permissions`, теперь настоящий allow/deny, а не только «выдать сверх
  роли») → **роль** (`staff_role_permissions`, с дефолтами в `DEFAULT_ROLE_PERMISSIONS`, если
  тенант ничего не настраивал).
- Роль в `req.user` берётся **свежей из БД на каждый запрос** (`jwt.strategy.ts`), а не из JWT,
  выданного при логине — раньше смена роли не действовала, пока сотрудник не перелогинится.
- Персональные права ключуются `staff_users.id` (не `users.id` — это два разных UUID для одного
  человека, связаны только по `tenantId+email`). Токен несёт оба: `userId` (users.id) и
  `staffUserId` (staff_users.id, резолвится в `JwtStrategy.validate()`).
- Фронтенд: `MainLayout.tsx`'s `canAccess()` — та же логика (override → роль), берёт роль и id
  сотрудника из живого списка `/staff-users` (`currentStaff`), а не из `localStorage`,
  зафиксированного при логине.
- UI: `/staff/permissions` → вкладка «Сотрудники» → карточка сотрудника — три состояния на
  модуль (Запретить / Роль / Разрешить), не бинарный чекбокс.

**Формат прав всё ещё модуль-уровня** (`PermissionKey` — `leads`, `sales`, `products` и т.п., у
части модулей есть под-права типа `products_manage_fields`), НЕ поле/действие-уровня. Именно это
пользователь просит расширить (раздел 3).

## 2. Диагноз конкретной жалобы (Vlady, роль «Продажи», индивидуально разрешены «Лиды» и другое — но не видит)

Проверено напрямую в БД и через `RbacService.canForUser()` (реальный код, реальные данные этого
сотрудника, без иммитации):

- `staff_users.role` и `users.role` = `sales`, синхронны.
- Сохранённая матрица роли `sales` для этого тенанта явно включает `leads`, `sales`, `contacts`,
  `companies`, `products`, `projects`, `analytics` (не дефолт — тенант её кастомизировал на
  вкладке «Роли и права», и там ЕСТЬ доступ).
- Персональные исключения Vlady (7 штук) — все `allowed: true`, дублируют то, что и так даёт
  роль (избыточно, но не вредно).
- `RbacService.canForUser(tenantId, staffUserId, 'sales', 'leads')` → **`true`**. Аналогично для
  `sales/contacts/companies/notes/products/projects/analytics`.
- `tenants.enabledComponents`/`enabledModules` (тумблеры pl1) — `leads` и все проверенные модули
  **включены** на уровне тенанта.

**Вывод: бэкенд корректно решает, что доступ должен быть.** Раз реальный логин Vlady всё равно
показывает пусто — почти наверняка **у него открыта старая вкладка/сессия браузера**, в которой
React-приложение продолжает работать со SPA-состоянием, загруженным ДО сегодняшних правок (роль
из `localStorage`, зафиксированная при более раннем логине, до того как её сменили на «Продажи»,
и/или до деплоя сегодняшних фиксов). Это одноразовая SPA — деплой на сервере не обновляет уже
открытую вкладку сам по себе.

**Что нужно сделать пользователю, прежде чем разбираться дальше**: попросить Vlady сделать
**жёсткий релогин** (выйти из аккаунта, закрыть вкладку, зайти заново — не просто F5, т.к. кэш
браузера может отдать старый JS) или открыть CRM в приватном/инкогнито-окне. Если после этого
проблема повторится — писать сюда с точным списком того, что не видно, и по возможности
скриншотом Network-вкладки браузера (`GET /v1/rbac/staff-permissions`,
`GET /v1/rbac/user-permissions`, `GET /v1/staff-users` — их реальные ответы для этой сессии).

## 3. Что просит пользователь — расширение RBAC

Дословно: «надо более глубокий RBAC. Чтоб прям к конкретным пунктам можно было закрывать доступ,
видимость, редактирование». Примеры, которые пользователь называл:

1. Закрывать/открывать доступ не только к модулю целиком («Лиды»), а к конкретным операциям
   внутри — например, **редактирование цены/суммы сделки**, **смена ответственного**.
2. Модуль «Маркетинг» — в контексте общей просьбы (не обязательно баг: см. раздел 2, у роли
   «Продажи» на этом тенанте `marketing` сейчас действительно не включён — это то, как тенант
   сам настроил роль, а не дефолт).
3. **AI-ассистент/AI-сотрудники не должны обходить права.** Дословно: «сам ИИ может быть включен,
   но чтоб по запросу к ИИ сотрудник не мог что-то поменять, если у него нет доступа». Это не
   гипотетическая просьба — при проверке (раздел 4) подтверждён реальный, уже существующий баг
   именно в эту сторону.

## 4. Найденные реальные пробелы (не гипотезы — прочитан код)

Проверено чтением `backend/src/ai/ai-tools.service.ts` (112 `tool*`-обработчиков AI-инструментов,
которые выполняются от имени тенанта, когда сотрудник просит что-то у AI-чата/AI-сотрудника):

- Единственная точка входа, `ai.controller.ts`, требует только **`chat: write`** на весь чат
  целиком. Дальше AI сам решает, какой инструмент вызвать — **без единого общего гейта на
  уровне запроса**, проверки разбросаны (или отсутствуют) по каждому инструменту отдельно.
- **31 инструмент** используют `checkPermission(ctx, key)` → реально дергают
  `RbacService.can(tenantId, role, key)` — **но это старый, только-по-роли метод**, не
  `canForUser()`. Персональные allow/deny-исключения (раздел 1) **AI-инструменты полностью
  игнорируют**, даже там, где проверка вообще есть.
- **6 инструментов** (`toolCreateLead`, `toolCreateProject`, `toolUpdateLead`,
  `toolUpdateProject`, ещё несколько) используют `hasAnyRole(ctx, ['owner','manager','sales'])`
  — **хардкод списка ролей прямо в коде**, скопированный из старой логики REST-контроллеров.
  Это означает: если владелец в «Ролях и правах» явно ОТКЛЮЧИЛ `leads` у роли `sales`, AI всё
  равно даст сотруднику с ролью `sales` редактировать лиды — потому что эта проверка вообще не
  смотрит ни в `staff_role_permissions`, ни в `staff_user_permissions`, только на строку роли.
- **`toolUpdateLead` (и его аналог для сделок/проектов) — универсальный `patch`**: принимает
  любой набор полей из аргументов AI и пишет их одним вызовом `leadsService.updateForTenant()`.
  Нет разбивки на «сотрудник может поменять статус» vs «сотрудник может поменять сумму» — так
  что даже если завтра появятся granular-права типа `leads_edit_amount`, AI-инструменту сейчас
  physically негде их применить: он не знает, какое из полей `patch`-а к какому праву относится.
- Оставшиеся ~75 инструментов (в основном чтение: `toolGetProject`, `toolListLeads` и т.п.) —
  **вообще без проверки прав**. Для read-инструментов это может быть осознанным решением (как и
  часть REST-эндпоинтов), но не проверено систематически.
- Отдельно, не про AI: `staff-users.controller.ts` **не имеет `RbacGuard` вообще** — только
  `JwtAuthGuard`. Любой залогиненный сотрудник, независимо от роли/прав, может дёргать
  `GET /staff-users` (список всех сотрудников тенанта). Найдено ещё в раунде «Departments» и
  зафиксировано как незакрытый долг — теперь подтверждено повторно при тестировании этой фичи.

## 5. Архитектурный выбор для поля/действие-уровня прав

Нужно решить, **как** моделировать «право редактировать конкретное поле», прежде чем писать код.
Два реалистичных варианта:

**Вариант A — расширить список `PermissionKey` под конкретные операции**, по образцу уже
существующих `leads_view_roi`, `products_manage_fields`, `projects_manage_trash` и т.п. Для
запроса пользователя это будет что-то вроде `leads_edit_amount`, `leads_edit_assignee`,
`sales_edit_amount`. Плюсы: минимальное изменение архитектуры — тот же `PermissionKey` union,
та же таблица, тот же UI-паттерн (уже есть child-права в `UserPermissionModuleList`/
`PermissionModuleList` — см. `GROUPS` в `StaffPermissionsPage.tsx`). Минусы: у каждого нового
редактируемого поля — новый ключ и явная точка проверки в контроллере/сервисе; для «любого
поля» это будет расти долго и вручную, только под явно запрошенные поля (цена, ответственный),
не универсально.

**Вариант B — реализовать давно существующий, но нигде не используемый `action` параметр**
(`read`/`write`/`delete`, разбор уже есть в `@RequirePermission`, но `RbacGuard` его игнорирует
— см. `lumiva_rbac_granularity_normalization` память) и добавить третье измерение — не поле, а
именно **тип операции** (просмотр / любое изменение / удаление) на уровне модуля. Это не даёт
«запретить именно цену, но разрешить статус» — только «запретить любое изменение, разрешить
просмотр». Дешевле реализовать, но не покрывает буквальный запрос пользователя (цена отдельно
от ответственного).

**Рекомендация**: Вариант A, но **не для всех полей всех модулей сразу** — только для полей,
которые пользователь явно назвал (цена/сумма, ответственный), на модулях Leads/Sales/Projects
(они и так уже частично гранулярны — см. `leads_view_roi`), и заложить схему так, чтобы дальше
добавлять по одному ключу за раз, а не проектировать сразу «универсальный движок полей». Схема
`staff_role_permissions`/`staff_user_permissions` уже поддерживает произвольные строки в колонке
`permission` — новой миграции для самих ключей не нужно, только код проверки на бэкенде + новые
позиции в `GROUPS`/`crm-ai-tool-definitions` на фронте/AI.

## 6. Фазы реализации (делать по одной, подтверждать перед следующей)

### Фаза 1 — ГОТОВО (2026-09-01)
- `checkPermission()` (используется во всех 31 вызовах) теперь дёргает `RbacService.canForUser()`
  вместо `can()` — персональные исключения (allow/deny) реально действуют и в AI-чате, не только
  в обычном UI. `ToolCtx` получил новое поле `staffUserId`, прокинутое через весь путь:
  `JwtStrategy` → `ai.controller.ts`/`telegram-crm.service.ts` (второй, ранее не замеченный
  вызов `runChat` — сотрудник, пишущий AI-ассистенту через Telegram, а не клиентский бот) →
  `ai-assistant.service.ts` → `AiToolsService.execute()`.
- Все 5 мест с хардкодом `hasAnyRole(ctx, ['owner','manager','sales'])`
  (`toolCreateLead`/`toolCreateProject`/`toolUpdateLead`/`toolUpdateProject`/
  `toolChangeProjectStatus`) заменены на `checkPermission(ctx, 'leads'|'projects')` — теперь
  используют реально настроенную тенантом матрицу ролей и персональные исключения, а не
  захардкоженный список. Мёртвый метод `hasAnyRole` удалён.
- **Найдена асимметрия, оставлена как есть осознанно**: у REST-контроллера
  (`leads.controller.ts:337`) для создания лида остался тот же хардкод
  `canCreateRoles = ['owner','manager','sales']` **в дополнение** к RBAC-гварду — это отдельный,
  более старый пласт кода, не тронутый в этом раунде (риск сломать реальный, уже работающий UI).
  Практический эффект: сейчас AI **строже уважает** индивидуальные исключения, чем REST для этого
  конкретного действия (создание лида) — если понадобится полная симметрия, надо отдельно чистить
  `leads.controller.ts`/`projects.controller.ts` от аналогичных хардкодов (не входило в этот
  раунд, но сам факт похожего хардкода в REST — ещё один повод сделать это в фазе 4 или отдельно).
- **Верифицировано вживую**, не только тестами: одноразовый тестовый тенант +
  `AiToolsService.execute('crm_create_lead', ...)`/`execute('crm_create_project', ...)` напрямую
  (не через LLM) — (1) роль без базового доступа блокируется, (2) роль С базовым доступом, но с
  персональным deny-исключением, тоже блокируется (главная новая гарантия), (3) без исключений
  запрос по-прежнему проходит проверку прав дальше (allow-путь не сломан). Тестовый тенант удалён
  после.
- **Не сделано в этой фазе, осознанно отложено**: систематическая проверка ~75 read-инструментов
  без единой проверки прав (не решено, какие из них должны требовать `PermissionKey` на чтение) —
  и отдельно, `ai-employees.service.ts` (автономные AI-агенты, `agentId` вместо `staffUserId`,
  сейчас `checkPermission` для них молча падает на роль `'viewer'` по умолчанию, т.к. `userRole`
  не передаётся) — там принципиально другая модель идентичности, нужно отдельное решение, чьи
  права должен наследовать агент.

### Фаза 2 + 3 — ГОТОВО (2026-09-01)

**Итоговые ключи оказались не совсем те, что были в первоначальном черновике плана** — при
чтении реального кода выяснилось, что «сумма» и «ответственный» существуют по-разному в разных
модулях, поэтому симметричный набор из 6 ключей был бы частично бессмысленным:

- `leads_edit_amount` — реальное, ранее ничем не защищённое поле. По умолчанию наследует базовое
  `leads` (`GRANULAR_FALLBACK_TO_BASE`) — не сужает никого без явной настройки.
- **`leads_edit_assignee` НЕ добавлен.** У Лидов уже есть отдельная, более сложная система
  назначения — `LeadAccessService` (тиры viewer/analyst/editor/owner, гранты по источнику),
  которая и решает, кто может переназначить лид (`REASSIGN_FIELDS` в `LeadsController`). Второй,
  параллельный RBAC-тумблер на то же самое было бы дублированием/конфликтом, а не расширением
  контроля — ровно то, от чего предостерегает раздел 7 этого документа.
- `sales_edit_amount`/`sales_edit_assignee` — **НЕ добавлены**: у Sale вообще нет `amount` в
  `UpdateSaleDto` (сумма не редактируется через API вообще, только при создании/импорте) и нет
  структурного поля ответственного (`managerName`/`agentName` — свободный текст, не FK). Гейтить
  здесь нечего — ключи были бы «висящими в воздухе». Если пользователь позже попросит сделать
  сумму продажи редактируемой — это отдельная фича (нужно менять DTO/сервис), тогда и добавить
  granular-право вместе с ней.
- `projects_edit_amount` — реальное поле, по умолчанию наследует базовое `projects` (как и было
  раньше — любой, кто мог редактировать свой проект, мог менять сумму).
  `projects_edit_owner` (не `_assignee` — назван по реальному полю `ownerUserId`/`ownerUserIds`/
  `ownerName`) — **без fallback на базовый ключ**, по умолчанию `false` для всех кроме owner: это
  сохраняет прежнее поведение (`ProjectsController` раньше хардкодил «только role==='owner' может
  менять владельца проекта»), просто теперь это настраиваемо через «Индивидуальные права» вместо
  зашитого в код списка, и с явным 403 вместо молчаливого игнорирования полей.
- Backend: `LeadsController.update()`/`ProjectsController.update()` проверяют новые ключи через
  `RbacService.canForUser()` (уважает персональные исключения, не только роль) до вызова сервиса.
  `ProjectsController` заодно избавился от собственного хардкода стрипа `ownerUserId` для
  non-owner — теперь явный 403 через тот же granular-ключ.
- AI (`toolUpdateLead`/`toolUpdateProject` в `ai-tools.service.ts`) проверяют те же самые ключи на
  тех же полях (`amount`, `ownerUserId`/`ownerUserIds`/`ownerName`) — раньше AI мог менять сумму
  проекта и переназначать владельца вообще без какой-либо проверки прав.
- Frontend: обе строки добавлены в `UserPermissionModuleList`'s `GROUPS` (child-права под `leads`/
  `projects`) — владелец может их настроить на вкладке «Сотрудники» → «Индивидуальные права».
  **Не сделано**: `LeadDetailPage`/`ProjectDetailPage` пока не скрывают/не дизейблят сами поля
  суммы/ответственного при отсутствии права — сохранение просто получит 403 с понятной ошибкой
  вместо тихого визуального disable. UX чуть хуже (сотрудник видит поле, но не может сохранить),
  данные защищены полностью. Можно доделать отдельным, чисто фронтендовым шагом.
- **Верифицировано вживую** (не только сборкой): одноразовый тестовый тенант, реальный HTTP —
  (1) `leads_edit_amount` без настройки наследует базовое `leads` (200), персональный deny блокирует
  именно сумму, но не остальные поля лида; (2) `projects_edit_owner` без настройки блокирует
  переназначение владельца (403) даже той же ролью, что раньше это разрешала; explicit allow
  снимает блокировку; (3) `projects_edit_amount` без настройки проходит (200, наследует базовое
  `projects`). Тестовый тенант удалён после.

### Фаза 4 — ГОТОВО (2026-09-01): staff-users.controller.ts

**Оказалось серьёзнее, чем предполагалось в черновике плана.** Это была не просто «нет RbacGuard
на списке» — на КАЖДОМ изменяющем эндпоинте контроллера вообще не было никакой проверки роли,
включая `PATCH :id/role`. Это значит, что **любой залогиненный сотрудник любой роли (включая
viewer) мог назначить сам себя владельцем компании** одним запросом — активная, не
гипотетическая privilege-escalation дыра в проде. `updateForTenant`'s единственная защита
(`if (user.role === 'owner' && patch.role !== 'owner') throw` — в `staff-users.service.ts`)
блокирует только понижение УЖЕ существующего owner'а, но не повышение кого угодно до owner.

Исправлено тем же паттерном, что уже применён в `rbac.controller.ts`/`departments.controller.ts`
(`assertOwner` по `req.user.role`, GET остаётся открытым для всех авторизованных — читают

## 8. Найденные после Phase 1-4 баги (2026-09-01)

**Баг: «меняю роль Продажи — не действует, меняю Менеджер — действует».** Не баг в коде RBAC —
`canForUser()` (override → role) работает корректно. Причина: у сотрудника Vlady
(`staff_users.id=b805c0b1-...`) обнаружено 24 персональных override-строки в
`staff_user_permissions`, почти все `allowed=false` (leads/companies/projects/sales/... — кроме
`leads_view_roi=true`), все с одним `created_at` (2026-09-01 12:43:19) — то есть один-единственный
сохранённый список из вкладки «Люди», а не что-то накопленное со временем. Персональный override
всегда побеждает роль (по дизайну, это и есть смысл индивидуальных прав) — поэтому любое изменение
роли Продажи не давало эффекта: override перекрывал его. Похоже на случайный клик по вкладке «Люди»
(ровно то, что пользователь и предположил: «может я куда-то нажал»). Исправлено: очистил все 24
override-строки для Vlady (`DELETE FROM staff_user_permissions WHERE user_id=...`) — теперь его
доступ снова полностью определяется ролью Продажи. Данных не потеряно — сама роль не трогалась,
override можно настроить заново осознанно через «Люди» при необходимости.

**UX: сырой «Forbidden resource» вместо дизайна — и регрессия от первой попытки.** Первая версия
фикса перехватывала 403 реактивно в `frontend/src/api/client.ts` (любой GET с 403 → редирект на
`/dashboard`). Оказалось катастрофично: `MainLayout` на КАЖДОЙ странице фонoво тянет счётчики для
бейджей меню (`Promise.all([fetchLeadsList(), fetchProjects()])`), и если у роли нет доступа к
лидам — этот фоновый вызов 403-ился и реактивный редирект уводил пользователя с ЛЮБОЙ страницы
(Проекты «включено, но не открывает», BI-дашборд «тоже не работает» — оба следствие одного и того
же). Правильное решение — не реагировать на 403 постфактум, а гейтить ПРОАКТИВНО на уровне роута:
`MainLayout` уже считает `permissionForPath(location.pathname)`/`canAccess(...)` для фильтрации
меню — теперь тот же расчёт (`routeAllowed`) применяется и к текущему пути ДО монтирования
`{children}` (см. `main` в `MainLayout.tsx`: `!routeAllowed` → показывает лоадер и в `useEffect`
делает `navigate('/dashboard')`, вместо рендера страницы). Раз страница не монтируется — её
собственные запросы вообще не улетают, никакого сырого 403 в принципе. `client.ts` откатил к
исходному поведению (просто `throw ApiError`), `persistForbiddenNotice`/`readForbiddenNotice` в
нём остались, но теперь вызываются из MainLayout при срабатывании route-гейта, не из HTTP-слоя.
Плашка на `/dashboard` (текст `crm.errors.accessDeniedTitle`/`accessDeniedText`) осталась той же.

## 9. Дальнейшие баги того же дня (2026-09-01, продолжение)

**Гонка редиректов «нет доступа».** Мой route-gate (раздел 8) оказался НЕ единственным механизмом —
в MainLayout уже был более старый `useEffect` (`isCrmShellPath` + `navigate('/forbidden', ...)`),
который я не заметил при первом проходе. Оба эффекта реагируют на одно и то же условие
(`!canAccess(permissionForPath(...))`) в одном рендер-цикле — старый шёл ПОСЛЕ моего по порядку
объявления и его `navigate('/forbidden')` побеждал мой `navigate('/dashboard')`. Плюс старый
проверял доступ только по узкому списку `roots` (не знал о `/products`, `/bookings`, `/hotels`,
`/helpdesk`, `/esign`, `/analytics`, `/bi` и т.д.). Убрал старый механизм целиком — мой route-gate
и так покрывает всё через `permissionForPath`/`componentKeyForPath`.

**Бейдж роли в шапке был статичным.** `staffRoleLabel` считался из `user.role` (localStorage,
фиксируется на логине), а не из `currentStaff.role` (свежая запись из `/staff-users`, как в
`canAccess()`). После смены роли сотруднику в шапке ЕГО СОБСТВЕННОЙ сессии ещё долго висела старая
роль — реальные права уже считались верно, но по бейджу невозможно было понять, что происходит.
Поправлено на тот же `currentStaff?.role ?? user?.role`.

**Самое серьёзное: бесконечный цикл перезапроса матрицы прав.** `useEffect` в MainLayout, который
грузит `roleMatrix`/`userMatrix` для не-owner (`fetchStaffPermissions`/`fetchUserPermissions`),
зависел от `[user]` — а `user = getStoredUser()` делает `JSON.parse(localStorage...)` заново на
КАЖДЫЙ рендер, то есть это всегда новая ссылка, даже когда содержимое не изменилось. Эффект
перезапускался на каждый рендер → новый fetch → `setRoleMatrix`/`setUserMatrix` (тоже новые ссылки
из JSON-ответа) → ре-рендер → `user` снова новая ссылка → эффект снова, без остановки. Данные это
впрямую не портило (есть `alive`-guard от гонки устаревшего ответа), но заливало бэкенд дублями
запросов почти без паузы и создавало ощущение «то работает, то нет» при проверке прав — что владелец
и наблюдал («ничего не работает если выбираю по роли», хотя сама база и `RbacService.can()`/
`canForUser()` при прямой проверке возвращали правильный `true` по всем ключам). В том же файле уже
был правильный паттерн для другого эффекта (`[user?.id, user?.sub]`, строка ~962) — этот эффект его
почему-то не использовал. Исправлено на `[user?.id, user?.role]`.

Проверено напрямую в БД/бэкенде на момент фикса: роль `manager` в тенанте `admin` имела 32
разрешённых права (включая `staff`, `settings`, `leads`, `projects`, `sales` и т.д.), у Vlady
(`staff_users.id=b805c0b1-...`, роль сейчас `manager`) — ноль индивидуальных override; `can()`/
`canForUser()` возвращали `true` по каждому проверенному ключу. То есть весь описанный "баг"
целиком объясняется фронтенд-гонкой запросов, не данными и не бэкенд-логикой.

## 10. Настоящий корень всей серии «роль поменял — не действует» (2026-09-01, финал)

Проверено в БД напрямую: `staff_users.role` И `users.role` оба уже `manager`, синхронны,
`jwt.strategy.ts` резолвит роль свежей из БД на каждый запрос без кэша — бэкенд был абсолютно
корректен. Нашёл настоящую причину в `MainLayout.tsx`: `canAccess()` берёт роль из
`currentStaff?.role ?? user?.role`, где `currentStaff = staff.find(...)` по состоянию `staff`
(`useState<StaffUser[]>([])`) — **а единственное место, где это состояние вообще заполнялось,
было побочным эффектом открытия панели уведомлений** (`loadTaskNotifications`, вызывается только
когда `notificationsOpen`/`notificationsPreviewOpen`). Нигде в компоненте не было отдельного
`useEffect`, который грузил бы список сотрудников на монтирование. То есть `currentStaff` был
`undefined` почти всегда, и `canAccess()` **молча откатывался на `user?.role`** — роль,
зафиксированную в localStorage/сессии в момент логина, которая никогда не обновляется до
релогина. Комментарий в коде утверждал обратное («currentStaff — свежая запись»), но реально
свежих данных там почти никогда не было. Добавлен отдельный `useEffect` (зависит от
`[user?.id, user?.role]`, как и два предыдущих фикса), который грузит `fetchStaff()` сразу при
смене пользователя, не дожидаясь колокольчика.

Заодно исправлен `frontend/src/hooks/usePermission.ts` (используется для виджетов дашборда и
пары granular-полей формы) — у него был СВОЙ, полностью независимый кэш на весь модуль, который
заполнялся один раз и не протухал никогда (до жёсткого релогина). Добавлен TTL 30 секунд вместо
вечного кэша — тот же класс бага, что и выше, просто в другом месте.

С этим фиксом должна закрыться вся цепочка: смена роли сотруднику теперь отражается на реальной
навигации без релогина в течение секунд, а не после случайного клика на колокольчик уведомлений.

## 11. Лиды: «скрыл сумму — а он даже открыть лид не может» (2026-09-01)

Настройки «Видимость данных» (вкладка «Видимость данных» на `/staff/permissions`) для лидов были
**чисто декоративными** — `DataVisibilityService`/`amounts_visibility`/`foreign_records`/
`contact_masking` реально применяются в `contacts.controller.ts`/`companies.controller.ts`/
`sales.controller.ts` (маскируют поля, не блокируют запись), но НЕ в `leads.controller.ts`. Там
действует отдельная, более старая система — `LeadAccessService`/`lead_access_grants` (доступ по
источнику лида, opt-in): нет назначения на лид И нет explicit-гранта на источник → `tierFor`
возвращает `'none'` → `GET /leads/:id` кидает 403 целиком, независимо от того, что настроено в
«Видимости данных». Отсюда и жалоба: поставили «Суммы сделок: только ответственному», а сотрудника
вообще не пускает в лид, где его тегнули в комментарии.

Сведены обе системы вместе в `leads.controller.ts` (по образцу уже работающего паттерна в
`sales.controller.ts`/`contacts.controller.ts`):

- `tierFor()`: если явного гранта/назначения нет — вместо жёсткого `'none'` теперь смотрит на
  правило `foreign_records` этой роли. `'hide'` — как раньше, недоступно. Что угодно другое
  (`'full'`/`'masked'`) — даёт read-only tier `'viewer'` (не разблокирует edit/delete/reassign,
  для этого по-прежнему нужен грант или назначение — `canEdit('viewer')` уже `false`).
- `decorate()`: добавлено маскирование `amount` (по правилу `amounts_visibility`) и `phone`/
  `email` (по правилу `contact_masking`) для не-владельцев/не-назначенных — применяется
  одинаково в списке, поиске и детальной карточке (один общий `decorate()`).
- `LeadAccessService.isAssigned` сделан публичным (`isAssignedTo`) для переиспользования в
  `decorate()`.
- `DataVisibilityModule` добавлен в импорты `LeadsModule` — раньше не был подключён вовсе.

Проверено: у роли `sales` в тенанте `admin` реально сохранено `amounts_visibility=owner_manager`,
`contact_masking=mask_until_assigned`, строки для `foreign_records` нет — значит применяется
дефолт `'full'` (не `'hide'`), то есть после фикса такой сотрудник **сможет открыть чужой лид**
(с замаскированными суммой/телефоном/email), а не получит 403.

## 12. Ещё два бага, найденные при живом тестировании (2026-09-01, вечер)

**«Лиды → Проекты — нет доступа, а с Главной работает».** Race condition в фиксе из раздела 10.
Добавленная там загрузка списка сотрудников (`fetchStaff()`) ни на что не была завязана по
готовности — `routeAllowed` мог посчитаться ДО того, как этот список пришёл, и `canAccess()` на
секунду откатывался на `user?.role` из localStorage (устаревшую роль). С Главной страницы это не
проявлялось — там долгая загрузка дашборда сама по себе давала время фоновому запросу
досчитаться; при быстрой навигации между двумя обычными страницами — не успевала. Добавлен
`staffLoaded` (аналогично `permsLoaded`/`componentsLoaded`) — экран загрузки/расчёт `routeAllowed`
теперь ждёт все три флага, не только два.

**Краш «Приложение не загрузилось» / `Failed to fetch dynamically imported module`.** Побочный
эффект того, что мы задеплоили фронтенд ~8 раз за сессию: у открытой вкладки `index.html` уже
ссылается на хэши чанков ИЗ ПРОШЛОГО билда, а `rsync --delete` их с сервера убрал — при попытке
подгрузить такой чанк браузер получает 404 и Vite бросает `vite:preloadError`, что уже наш
`ErrorBoundary` ловил как обычную непойманную ошибку и показывал краш-экран. Добавлено
самовосстановление (стандартный для Vite паттерн): слушатель `vite:preloadError` в `main.tsx`
делает один `location.reload()` (не более раза в 60 сек, флаг в sessionStorage — от зацикливания),
плюс тот же catch добавлен в `ErrorBoundary.componentDidCatch` как резерв для случая, когда ошибка
дошла как обычный React-throw, а не через `vite:preloadError`. Актуально не только для сегодня —
это будет происходить при КАЖДОМ будущем деплое, если у пользователя открыта вкладка.

## 13. Роль «Менеджер» убрана из привилегированных (2026-09-01, по явному запросу)

Раньше `manager` был жёстко закодирован как «видит всё» сразу в двух местах — `LeadAccessService.
FULL_ACCESS_ROLES` и `DataVisibilityService.PRIVILEGED_ROLES` — из-за чего правила «Видимость
данных» физически не могли ограничить менеджера: UI даже не давал выбрать роль «Менеджер» в
выпадающем списке настройки правил (`DV_ROLES` на фронте её исключал), а панель «Проверка на
сотруднике» честно писала «У этой роли нет ограничений по этим правилам». Пользователь подтвердил
осознанно: убрать `manager` из привилегированных ролей.

Изменено:
- `FULL_ACCESS_ROLES` → `['owner']` (было `['owner', 'manager']`) в `lead-access.service.ts`.
- `PRIVILEGED_ROLES` → `['owner']` (было `['owner', 'manager']`) в `data-visibility.service.ts`.
- Фронтенд `DV_ROLES` в `StaffPermissionsPage.tsx` больше не исключает `manager` — роль теперь
  настраивается на вкладке «Видимость данных» как любая другая (кроме владельца).
- Начальник отдела (`headsADepartment`) по-прежнему получает полный доступ независимо от роли —
  это отдельная, не тронутая ветка проверки.

**Важно — последствия шире, чем только лиды**: `foreign_records`/`amounts_visibility`/
`contact_masking` — общие правила для Лидов, Контактов, Компаний и Продаж (один и тот же
`DataVisibilityService`). Раз менеджер перестал быть привилегированным — эти правила теперь
реально действуют на менеджера ВЕЗДЕ, не только в Лидах, где был явный запрос.

**Проверено на реальных данных**: только у тестового тенанта `admin` вообще есть активный
сотрудник с ролью `manager` (Vlady) — ни один настоящий клиентский тенант сейчас не использует эту
роль, риск для существующих клиентов нулевой. Компилированный `dist/*.js` в живом образе после
пересборки подтверждён напрямую (`grep` внутри контейнера) — `FULL_ACCESS_ROLES`/
`PRIVILEGED_ROLES` действительно равны `['owner']`.

Дополнительно, раз это уже настроено для роли `sales` в этом тенанте (правило «Скрывать
полностью» на скриншоте пользователя) и по факту то же самое просили для менеджера — сразу
проставил `foreign_records='hide'` для роли `manager` в тенанте `admin` (была одна кастомизация:
до этого у роли `manager` не было вообще ни одной строки в `staff_data_visibility_rules`, поэтому
без явного значения `getRuleValue()` продолжал бы возвращать дефолт `'full'` — то есть само по
себе удаление роли из привилегированных ничего бы не изменило, пока владелец не настроил бы
правило вручную). `amounts_visibility`/`contact_masking` для `manager` оставлены на дефолте —
не трогал, это отдельное решение владельца, если понадобится.
