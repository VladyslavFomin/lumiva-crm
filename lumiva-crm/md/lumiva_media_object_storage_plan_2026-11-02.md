# Медиа → облачное хранилище (Backblaze B2 + Cloudflare) — план

Статус: **не начато** (план от 2026-11-02, реализация — позже).

## Зачем

- Сервер — один VPS с диском 96 ГБ, на 2026-11-02 занято 96% (свободно 4,5 ГБ). На нём всё сразу: БД, Docker, сайты, логи, файлы.
- Медиа лежит в docker-томе `infra_lumiva_crm_uploads` → `/app/uploads/media/<tenantId>/…` (~2,5 ГБ).
- Ожидание: 2,5–4 ГБ на отель; 20 отелей = 50–80 ГБ, дальше растёт с числом тенантов. Любой локальный диск (даже 200 ГБ) — тупик.
- Объектное хранилище не имеет потолка, платим за фактический объём (B2 ≈ $6/ТБ/мес — проверить актуальную цену при подключении), отдача через Cloudflare у B2 бесплатна (Bandwidth Alliance).

## Что нужно от владельца (до начала)

1. В кабинете Backblaze **поднять/снять лимит расходов (Caps & Alerts)** — в октябре 2026 он уже срабатывал на бэкапах.
2. Создать **отдельный приватный bucket** под Медиа (например `lumiva-media`), не смешивать с бэкапами.
3. Создать **Application Key** только на этот bucket (read+write+delete). Ключ от бэкапов не переиспользовать.
4. (Опционально, этап 2) Домен для CDN, например `media-cdn.lumiva.agency`, через Cloudflare → B2.

Переменные в backend `.env`: `MEDIA_STORAGE=s3`, `MEDIA_S3_ENDPOINT` (https://s3.<region>.backblazeb2.com), `MEDIA_S3_REGION`, `MEDIA_S3_BUCKET`, `MEDIA_S3_KEY_ID`, `MEDIA_S3_SECRET`, опц. `MEDIA_CDN_BASE`.

## Этапы

### 1. Абстракция хранилища + новые загрузки в B2
- `MediaStorage` (интерфейс): `put(key, stream|file)`, `getStream(key, range?)`, `head(key)`, `delete(key)`, `copy(src, dst)`, `signedUrl(key, ttl, disposition?)`. Две реализации: `LocalMediaStorage` (как сейчас) и `S3MediaStorage` (`@aws-sdk/client-s3` + `lib-storage` для multipart, B2 совместим).
- В `media_files` добавить `storageBackend: 'local' | 's3'` (миграция, дефолт `local`) — чтобы старые и новые файлы жили одновременно.
- Чанки по-прежнему собираются во временный файл на диске (они маленькие и живут минуты), после финализации: qpdf/превью локально → выгрузка в B2 → удаление temp. Прямую загрузку из браузера в B2 (presigned multipart) — отложить, не нужна на старте.

### 2. Отдача файлов
- Просмотр/превью/скачивание для `s3`-файлов: редирект 302 на короткоживущую presigned-ссылку (или `MEDIA_CDN_BASE`). Range для видео и PDF-журнала тогда отдаёт B2 сам. Проверить CORS bucket для pdf.js (Range-запросы из браузера).
- Публичная страница `/m/:slug`, токены доступа и счётчики скачиваний остаются на нашем API — меняется только финальная выдача байтов.
- ZIP папки: стримить объекты из B2 в `archiver` (без сохранения на диск).
- Дублирование коллекции: `CopyObject` на стороне B2.

### 3. Квоты
- Перевести учёт Медиа на `SUM(media_files.size)` по тенанту (а не по диску). Остальные модули (uploads вне media) пока остаются на дисковом учёте.
- Пересмотреть лимиты тарифов (сейчас 3/5/10 ГБ на тенанта — `tenants/storage-quota.util.ts`): либо поднять для Медиа, либо платная опция «доп. хранилище» в pl1. Решение — за владельцем.

### 4. Перенос существующих файлов
- Одноразовый скрипт: для каждого `local`-файла → upload в B2 → `head` проверяет размер → `storageBackend='s3'` → удалить локальный файл. Идемпотентно, батчами, с логом. ~2,5 ГБ на 2026-11-02.
- После переноса `LocalMediaStorage` оставить как fallback для dev/тест-стендов.

### 5. Бэкап
- Убрать media-архив из `backup_lumiva_crm.sh` (после переноса папка будет пустой).
- В bucket включить версионирование (Lifecycle: хранить удалённые/старые версии N дней) — это и есть бэкап Медиа.

## Проверка
- Загрузка большого видео (>1 ГБ) и PDF-каталога, перемотка видео, листание PDF-журнала, скачивание, ZIP папки, дублирование коллекции, удаление — на тест-тенанте, для `local` и для `s3` файлов.
- Квота: загрузка сверх лимита отклоняется.
- Мобильное приложение: экраны Медиа используют те же URL — проверить, что редиректы проходят.
