# Интеграция PMS с туроператорами — план (2026-11-02)

Статус: **план, код не начат**. Основа уже выложена: у брони есть `voucherNo`, у партнёра — карточка, контракты и квоты, менеджер каналов (Channex) даёт готовый каркас «подключение → сопоставление → загрузка броней → подтверждение получения».

Цель: брони туроператоров (ТО) попадают в PMS сами, без перепечатывания. Каждое изменение и отмена у ТО находит свою бронь по ваучеру. Ни одна бронь не теряется, не дублируется и не перезаписывает работу ресепшена.

---

## 1. Как это устроено в отрасли (по фактам, а не по догадкам)

### 1.1. Кто кому передаёт брони

Схема продаж в Турции: **ТО за рубежом** (Anex, Pegas, Coral, TUI, FTI…) → **incoming-агентство** в Турции (часто дочерняя компания того же ТО) → **отель**. Контракт и расчёты отель обычно ведёт с incoming-агентством, а в броне видно и агентство, и исходного ТО.

Каждое incoming-агентство работает в своей учётной системе. Отелю брони видны одним из четырёх способов:

| Способ | Пример | Как PMS получает бронь |
|---|---|---|
| **Документированный API для PMS** | Sejour → платформа **Hotel2Sejour** (SanTSG) | PMS сама забирает список броней, отмечает принятые и отправляет подтверждение |
| **Веб-кабинет отеля (экстранет)** | SAMO-Incoming → модуль **Hotel-office**; кабинеты Anex, Pegas, TUI (Destimo / Partners), Odeon | Отель заходит под своим логином. API не опубликован, есть письма-уведомления и выгрузка в Excel |
| **Письмо / факс / PDF-ваучер** | Почти все ТО, особенно мелкие | Письмо в почту отеля |
| **Через менеджер каналов** | TravelLine (РФ), Booking.com, Expedia и т.п. | У нас уже работает через Channex |

### 1.2. Как это делает лидер рынка Турции — Elektraweb

У Elektraweb есть модуль «Tur Operatörü Entegrasyonu». Отдельные инструкции есть для Anex, Pegas, Sejour, Sejour 2, TUI (Destimo и Partners, включая UK), Odeon, ETS, Motus, Novanta, Otelsnet, Sedna, TatilBudur, WHTUR и EasyJet.

**Механика.** Установленная на компьютер отеля программа заходит в систему ТО под учётными данными отеля: «ID отеля у оператора», «код пользователя», «пароль», при нескольких отелях — «код пользователя 2» с точным названием отеля в системе ТО. Программа забирает брони по фильтру: дата проживания или дата продажи, статус, тип.

**Сопоставление.** Перед первой загрузкой включается режим «Eşleştirme». Из загруженных броней создаются строки сопоставления:
- тип номера ТО → тип номера отеля;
- план/питание ТО → питание и тариф отеля;
- агентство ТО → карточка агентства в PMS.

**Сохранение.** Человек отмечает брони и нажимает «PMS'e Kaydet». **Автоматически ничего не сохраняется.**

**Цена.** Брони сохраняются по ценам **контракта агентства в PMS**, а не по цене, которую прислал ТО.

Выводы для нас:
1. Отрасль приняла **ручное подтверждение загрузки** и **обязательное сопоставление кодов**. Это защита от ошибок, а не неудобство.
2. Цена брони считается **по нашему контракту с партнёром**. Цену ТО храним для сверки.
3. Для Anex, Pegas, TUI и Odeon Elektraweb, судя по всему, читает **веб-кабинеты** (окно ТО открывается и закрывается само). Публичных API этих ТО я не нашёл.

### 1.3. Sejour / Hotel2Sejour — единственный открытый API (точные данные из документации SanTSG)

- Вход: `GET /api/system/login?user=&pass=` возвращает токен, дальше он передаётся заголовком `cookie`. Ответ всегда `{ Data, Error{Code,Message}, InfoMessage, IsSuccessful }`.
- `GET /api/pax/gethotelagencies` — агентства, которые продают этот отель (Id GUID, Name).
- `GET /api/pax/getsejourformapping?paximumId&agencyId` — справочники для сопоставления: питание, национальности, типы номеров, номера.
- `GET /api/pax/getReservationList?checkInStart&checkInEnd&paximumId&agencyId&status&IsSendRequired=true`:
  - даты в формате **мм.дд.гггг**;
  - большой список приходит не сразу, а как `FileCode`, который забирается через `checkreservationfile`;
  - `IsSendRequired=true` означает «только то, что ещё не подтвердили как полученное».
- Поля брони:
  - идентификаторы: `KeyField`, `ServiceId`, `LogId`, `VoucherNo`, `ConfirmationNo`;
  - агентство и ТО: `AgencyId/AgencyName`, `TourOpCode/TourOpName`;
  - проживание и номер: `CheckIn/CheckOut/Nights`, `Adults/Childs/Infants/Pax/RoomCount/ExtraBed`, `RoomId/RoomName/RoomTypeId/RoomTypeName/AccomId/AccomName`;
  - статусы: **`PmsStatus` 0 = новая, 2 = изменение, 3 = отмена**; `ReservationStatus` 0 Ok / 1 OnRequest / 2 NoShow / 3 GoShow / 4 Option; `QuotaType` 0 гарантия / 1 обычная / 2 по запросу;
  - отметки: `FreeOfCharge`, `HoneyMoon`;
  - цена и продажа: `SoldPrice/SoldCurrency`, `SellDate`;
  - прочее: `Note`, `ExtraServices`;
  - гости `Customers[]`: `Name`, `Title`, `Age`, `BirthDate`, `Nationality`, `Arrival/ArrivalTime`, `Departure/DepartureTime` (рейсы).
- `POST /api/Pax/postsentlogids` (`serviceId`, `logIds`) — «получено», после этого бронь не придёт повторно, пока не изменится.
- `GET /api/pax/sendconfirmation` — ответ отеля: `E` подтвердить / `H` отказать (с причиной из `getnotconfirmmessages`), комментарий до 500 символов. V2 дополнительно возвращает ссылку на PDF-ваучер.
- ⚠ В документации только тестовый хост `admin.stage.hotel2sejour.com`, страницы датированы 2017 годом, у части методов не указан путь. **Рабочий адрес, актуальную версию API и доступы нужно получить у SanTSG.** Нельзя полагаться только на документацию.

### 1.4. SAMO (SAMO-Incoming / Hotel-office)

- Отель работает в браузере: видит заявки, подтверждает («Подтверждено» / «Не подтверждено» / «Ожидание»), видит пометки «новая / изменена / отменена» и историю, получает письма о новых и изменённых заявках, выгружает списки туристов в Excel.
- **Публичного API для отеля нет.** XML-шлюз SAMO предназначен для выгрузки цен и туров, а не для приёма броней в PMS.
- Реальные пути для нас:
  - (а) разбирать письма-уведомления SAMO;
  - (б) импортировать Excel-списки туристов с сопоставлением по номеру заявки;
  - (в) запросить у самого incoming-агентства (не у SAMO-Soft) интеграцию — SAMO умеет отправлять «новые / изменения / аннуляции» во внешние системы принимающих компаний;
  - (г) читать веб-кабинет.
- Номер заявки SAMO — это и есть наш `voucherNo`.

### 1.5. Россия: Мастер-Тур (Megatec), TravelLine

Мастер-Тур передаёт брони отелей через свой модуль интеграции, в том числе в TravelLine. Отели в РФ получают брони ТО чаще всего через TravelLine Channel Manager. По приоритету рынков (сначала Турция, потом РФ) это **последний этап**.

## 2. Главные принципы (чтобы «не было ошибок»)

1. **Один формат для всех источников.** Каждый адаптер (Sejour, письмо, Excel, кабинет) превращает данные ТО в одну и ту же «ревизию брони ТО». Дальше работает одна общая, проверенная логика. Адаптер ничего не пишет в брони сам.
2. **Сначала входящие, потом бронь.** Каждая полученная ревизия сохраняется **как есть** (исходный JSON/XML/письмо) в журнал входящих **до** любой обработки. Ничего не теряется, и любую ревизию можно разобрать заново.
3. **Защита от дублей.** Уникальный ключ — (подключение, внешний ключ строки). Для Sejour это `KeyField`, для остальных — ваучер + порядковый номер номера. Повторная ревизия ничего не меняет (сравнение по отпечатку содержимого).
4. **«Получено» отправляем только после записи в базу.** Как у Channex: `postsentlogids` или отметка в источнике вызывается только после того, как бронь сохранена. Если сервер упал посередине, бронь придёт ещё раз, а защита от дублей её поглотит.
5. **Ничего не угадываем.** Если код номера, питания, агентства или ТО не сопоставлен, ревизия ждёт в очереди «Нужно сопоставить». Никаких «похоже на DBL — значит DBL».
6. **Владение полями.** ТО меняет только своё: даты, тип номера, питание, состав гостей, имена, рейсы, примечание ТО, статус. Отель владеет номером комнаты, фолио и оплатами, ранним заездом и поздним выездом, внутренними заметками и профилем гостя. Изменение от ТО **никогда** не затирает поля отеля.
7. **Опасные изменения — только через человека.** В очередь «Требует решения» идут:
   - отмена уже заселённой или выехавшей брони;
   - изменение дат или номера после заезда;
   - бронь в закрытых ночным аудитом днях;
   - превышение квоты контракта;
   - нет мест (овербукинг);
   - расхождение цены ТО с нашей больше порога;
   - бронь не найдена для изменения или отмены.
8. **Цена — по нашему контракту.** Бронь создаётся с партнёром, контрактом (авто-подбор, как сейчас), тарифом и ценой по движку цен. Цена ТО (`SoldPrice`) хранится рядом и показывается расхождение — ровно как в Elektraweb.
9. **Режим работы — на выбор отеля для каждого подключения:**
   - «Ручной» (по умолчанию, как в Elektraweb): всё попадает в «Входящие», сотрудник нажимает «Принять».
   - «Авто»: полностью сопоставленные и безопасные ревизии применяются сами, остальные ждут во «Входящих».
10. **Всё в истории брони.** Каждое изменение от ТО пишется в историю как «Изменено туроператором (Sejour · Kartaca Tour) — было / стало».

## 3. Модель данных

### 3.1. Новые таблицы

**`hotel_to_connections`** — подключение отеля к источнику (по образцу `hotel_channel_connections`):
- `tenantId`, `hotelId`, `provider` (`sejour` | `samo_mail` | `email` | `excel` | позже панели ТО);
- `status`, `mode` (`manual` | `auto`), `environment`;
- учётные данные — **только в зашифрованном виде** (как `apiKeyEnc`): логин, пароль, ID отеля у оператора (`paximumId`), «код пользователя 2»;
- `settings` (окно загрузки по датам заезда, порог расхождения цены, автоподтверждение ТО);
- `lastPullAt`, `lastError`, `failCount`, `backoffUntil`.

**`hotel_to_mappings`** — сопоставление кодов:
- `connectionId`, `kind` (`room` | `board` | `agency` | `operator` | `nationality` | `market`);
- `externalCode`, `externalName`, ссылки на наши сущности (`roomTypeId` / `occupancyTypeId` / `boardType` / `ratePlanId` / `agencyId` / `marketId`), `active`;
- строки создаются **автоматически из первых загруженных броней** со статусом «не сопоставлено», как в Elektraweb.

**`hotel_to_inbox`** — журнал входящих ревизий:
- `connectionId`, `externalKey`, `voucherNo`, `externalAgency`, `externalOperator`;
- `kind` (`new` | `modify` | `cancel`), `payloadRaw` (исходные данные), `normalized` (наш общий формат), `hash`;
- `state` (`pending` | `needs_mapping` | `needs_decision` | `applied` | `ignored` | `failed`), `reason` / `blockers[]`;
- `reservationId`, `appliedAt`, `appliedBy` (пользователь или «авто»), `ackedAt` (когда отправили «получено» источнику).

**`hotel_to_links`** — бронь ↔ внешняя строка:
- (`connectionId`, `externalKey`) **уникально** → `reservationId`;
- `lastHash`, `lastExternalStatus`;
- `confirmationSentAt` / `confirmationStatus` (что ответили ТО: подтверждено / отказ).

### 3.2. Изменения существующего

- `hotel_reservations`:
  - `voucherNo` уже есть;
  - `source` получает значение `'tour_operator'`;
  - `externalAmount` + `externalCurrency` — цена ТО для сверки;
  - `operatorName` — исходный ТО за агентством (TUI / FTI…), если агентство и ТО разные;
  - рейсы прилёта и вылета пишем в данные гостей (`guests[]`), это уже jsonb.
- `hotel_agencies`: связь «агентство ↔ внешние коды» — через `hotel_to_mappings`, а не новыми полями карточки.
- **Многономерные ваучеры.** Один ваучер на N номеров становится N броней с одним `voucherNo` (у Sejour каждая строка имеет свой `KeyField`). При необходимости их можно объединить в «Группу» (модуль уже есть).

## 4. Общий конвейер (одинаковый для всех источников)

```
адаптер.fetch() ──► inbox (исходные данные + общий формат + отпечаток) ──► разбор ──► решение ──► применение ──► «получено» источнику
```

**1. Разбор (normalize).** Исходный формат → общий:
- даты (у Sejour мм.дд.гггг, в письмах — что угодно) → ISO; ночи, посчитанные из дат, сверяются с `Nights`;
- возрасты детей: из `BirthDate` на **дату заезда** (у нас есть `ageOn`), иначе из `Age`; младенцы — по правилу младенца отеля;
- гости: имя, фамилия, титул, дата рождения, гражданство (ISO-2 через наш `normalizeCountry`), паспорт, если есть, рейсы;
- статус: новая / изменение / отмена + опция / по запросу → наш `pending` с `optionUntil`.

**2. Сопоставление.** Коды номера, питания, агентства и ТО → наши ID. Чего-то нет → `needs_mapping`, бронь не создаётся.

**3. Проверки** — собираем причины (`blockers`), ничего не меняя:
- поиск существующей брони: сначала по ссылке (`hotel_to_links`), затем по (партнёр + ваучер) — это ловит брони, введённые вручную раньше интеграции;
- если найдена ручная бронь с тем же ваучером — **предлагаем связать**, не создаём вторую;
- наличие мест, квота контракта, стоп-продажи, минимальный срок проживания — через существующие проверки при создании брони;
- для гарантированной квоты (`QuotaType=0`) разрешаем принять даже при переполнении, но с явной пометкой «овербукинг по гарантии»;
- закрытые аудитом дни, заселённая бронь, отменённая бронь (воскрешение — только вручную);
- сравнение цены ТО и нашей.

**4. Применение** — только через существующие `HotelReservationsService.create/update/cancel`, а не прямыми SQL-записями:
- работают все текущие правила: цены, история, автоматизации, инвентарь каналов (ARI), брони для KBS;
- одна транзакция: бронь + `hotel_to_links` + состояние входящей записи.

**5. «Получено» источнику** — после успешного сохранения (`postsentlogids`). Ошибка отправки не откатывает бронь: повторим, защита от дублей поглотит повтор.

**6. Подтверждение ТО** — отдельное действие:
- кнопки «Подтвердить ТО» / «Отказать (причина)»;
- либо автоподтверждение по настройке подключения;
- в подтверждение уходит наш номер брони (`bookingCode`).

### Сценарии, которые обязаны пройти e2e

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Новая бронь, всё сопоставлено, режим «авто» | 1 бронь, ссылка, «получено» отправлено, история «Создано туроператором» |
| 2 | Та же ревизия пришла повторно | Ничего не изменилось, повторное «получено» |
| 3 | Изменение дат | Даты и цена пересчитаны, номер комнаты сохранён, если свободен, иначе снят с пометкой |
| 4 | Изменение пришло раньше «новой» (потеряли) | Создаётся как новая (upsert) |
| 5 | Отмена неподтверждённой и не заселённой | Отменена, причина «Отмена туроператором», штраф по политике контракта |
| 6 | Отмена заселённой | «Требует решения», бронь не тронута |
| 7 | Неизвестный тип номера | `needs_mapping`; после сопоставления «Повторить» → создана |
| 8 | Ручная бронь с тем же ваучером уже есть | Предложение связать; после связки изменения идут в неё |
| 9 | Ваучер на 3 номера | 3 брони, один `voucherNo`, разные внешние ключи |
| 10 | Квота контракта исчерпана | Обычная → «Требует решения»; гарантия → принята с пометкой |
| 11 | Цена ТО ≠ нашей больше порога | Бронь по нашей цене + флаг расхождения во «Входящих» |
| 12 | Ребёнок: дата рождения дана, возраст на заезд другой | Возраст считается на дату заезда |
| 13 | Сбой сервера между сохранением и «получено» | Повторная загрузка → без дублей |
| 14 | ТО сменил гостя / количество гостей | Состав обновлён, профиль гостя пересопоставлен, KBS-статус сброшен |
| 15 | Изменение затрагивает дни, закрытые аудитом | «Требует решения» |
| 16 | Отменённую бронь «вернули» новой ревизией | «Требует решения» (воскрешение только вручную) |
| 17 | Неверный пароль / 401 | Подключение «ошибка», пауза с увеличением интервала, уведомление владельцу, брони не тронуты |
| 18 | Большой список (`FileCode`) | Файл дождались и разобрали, ничего не пропущено |

## 5. Интерфейс

- **Отели → Партнёры → вкладка «Интеграции»** (или отдельный раздел «Туроператоры»): подключения, статус, последняя загрузка, ошибки, кнопки «Проверить подключение» и «Загрузить сейчас».
- **Сопоставление**: таблицы «код ТО → наш тип номера / питание / агентство / ТО». Несопоставленные строки сверху, жёлтым — как в Elektraweb.
- **Входящие** (главный рабочий экран):
  - вкладки: «Новые», «Нужно сопоставить», «Требует решения», «Применено», «Ошибки»;
  - по каждой ревизии — что придёт / что изменится (было → стало), причины блокировки;
  - кнопки «Принять», «Связать с бронью…», «Игнорировать», «Повторить»;
  - массовое «Принять выбранные».
- **Карточка брони**: блок «Туроператор»: источник, ваучер, ТО, статус подтверждения ТО, цена ТО и расхождение, кнопки «Подтвердить / Отказать ТО», ссылка на исходную ревизию.
- **Счётчик во «Входящих»** в меню и событие для «Автоматизаций» («пришла бронь от ТО», «ТО отменил»).

## 6. Этапы

### Этап A — фундамент + источники, не требующие доступов (можно начинать сразу)

1. Таблицы из §3, общий конвейер §4, экран «Входящие», сопоставление, блок в карточке.
2. **Импорт Excel/CSV с распознаванием по ваучеру.** Повторная загрузка списка ТО (rooming list, выгрузка Hotel-office SAMO) не плодит дубли: та же строка → без изменений, изменённая → изменение, пропавшая → «Возможно отменена?» (только подсказка, без автоотмены).
3. **Почта ТО.** Отель подключает свой ящик (наш `TenantMailService`) или пересылает письма ТО на отдельный адрес. ИИ извлекает поля из письма или PDF-ваучера в общий формат. **Письма только во «Входящие», никогда в авто-режим**: ИИ может ошибиться, человек смотрит «было → стало». Числа и даты дополнительно проверяются кодом: ночи = выезд − заезд, количество гостей = числу имён.
4. Имитация источника (как `mock-channex.mjs`) и e2e на все 18 сценариев.

### Этап B — Sejour / Hotel2Sejour (первый настоящий API)

- Адаптер по §1.3: вход по токену, загрузка с `IsSendRequired=true` за скользящее окно дат заезда (например, −3…+400 дней), обработка `FileCode`, справочники для сопоставления, `postsentlogids` после записи, `sendconfirmation` E/H.
- Расписание: раз в 5 минут, пауза с увеличением интервала при ошибках, ограничение частоты запросов.
- Одно подключение Hotel2Sejour = **много агентств** (`gethotelagencies`) → каждое сопоставляется с нашим партнёром. Внутри агентства — `TourOpCode` для финальной разбивки, если отель так считает выручку.
- **Нужно от владельца / SanTSG:** рабочий адрес API, логин и пароль Hotel2Sejour для отеля, `paximumId`, тестовый (stage) доступ. Без этого — только имитация.

### Этап C — SAMO и кабинеты ТО (Anex, Pegas, TUI, Odeon, Coral)

1. Сначала **официальный путь**: запросить у каждого incoming-агентства документацию API или XML-выгрузки для PMS. У SAMO-Incoming есть отправка «новые / изменения / аннуляции» во внешние системы — это настраивает агентство.
2. Если API нет: письма-уведомления (Этап A.3) + Excel-выгрузка (A.2) — работает уже сейчас.
3. Чтение веб-кабинета ТО (как делает Elektraweb) — **только по отдельному решению**:
   - это хрупко (любая смена вёрстки ломает загрузку);
   - юридически требует согласия ТО;
   - пароли отеля хранятся у нас.
   Если делать, то отдельный изолированный сервис с безголовым браузером, по одному адаптеру на кабинет, с проверкой «кабинет изменился → стоп и уведомление», а не тихие ошибки.

### Этап D — Россия (Мастер-Тур / TravelLine)

После Турции, по приоритету рынков. Скорее всего, через менеджер каналов или TravelLine API, а не напрямую с ТО.

## 7. Риски и как закрываем

| Риск | Защита |
|---|---|
| Дубль брони | Уникальный (подключение, внешний ключ) + поиск по (партнёр, ваучер) + отпечаток ревизии |
| Потерянная бронь | Сначала сырые данные во «Входящие», «получено» после записи, повторная загрузка за окно дат |
| Неверное сопоставление | Ничего не угадываем; несопоставленное ждёт; отчёт «какие коды пришли впервые» |
| ТО затёр работу ресепшена | Матрица владения полями (§2.6) |
| Автоотмена заселённого гостя | Запрещена, только «Требует решения» |
| Ошибка ИИ при разборе письма | Письма никогда не применяются автоматически, проверки кодом |
| Смена API / вёрстки у ТО | Мониторинг ошибок подключения, пауза + уведомление, сырые данные для повторного разбора |
| Персональные данные (паспорта, KVKK/GDPR) | Шифрование учётных данных, сырые данные с паспортами хранятся ограниченный срок (например, 180 дней после выезда), доступ по праву `hotels` |
| Часовые пояса | Даты заезда и выезда — календарные даты без времени, расписание — по времени отеля |

## 8. Что нужно от владельца перед стартом этапов B/C

1. **Список партнёров по каждому отелю**: какой ТО → через какое incoming-агентство → в какой системе (Sejour / SAMO / свой кабинет / только письма).
2. **Примеры**: 3–5 реальных писем или PDF-ваучеров от каждого ТО, включая изменение и отмену, и выгрузки Excel из кабинетов. На них строятся разбор и тесты.
3. **Доступы Hotel2Sejour** (тестовые, затем рабочие) — у SanTSG или через агентство, работающее на Sejour.
4. **Решение по чтению кабинетов** (Этап C.3): делаем или нет.
5. **Политика по умолчанию**: «ручной» режим для всех новых подключений (рекомендую), порог расхождения цены (например, 2 %), автоподтверждение ТО — выкл.
