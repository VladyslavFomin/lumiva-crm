# Кастомный домен тенанта — инструкция по настройке

Клиент может зайти в CRM под своим доменом (например `crm.clientcompany.com`) вместо
`crm.lumiva.agency`. Настраивается только нами, по запросу клиента — самообслуживания нет.
Бренд Lumiva остаётся как есть (это не white-label), интерфейс не меняется — меняется только
адрес и то, что на нём сразу открывается экран логина, а не маркетинговая главная.

**IP сервера: `195.35.56.237`** (тот же сервер, на котором крутится `crm.lumiva.agency`,
`pl1.lumiva.agency` и всё остальное). Именно на этот адрес клиент должен направить свой домен.

## Со стороны клиента

Всё, что нужно от клиента, — направить DNS его домена на наш сервер. Отправляем ему один из
двух вариантов (что примет его регистратор/DNS-панель):

**Вариант A — A-запись (обычно самый простой, подходит для любого поддомена):**

| Тип | Имя (Host/Name)       | Значение (Value)  | TTL      |
|-----|------------------------|--------------------|----------|
| A   | `crm` (для `crm.company.com`) | `195.35.56.237` | 300 или Auto |

**Вариант B — CNAME (если регистратор не даёт A-запись на поддомен или клиент предпочитает
привязку по имени, а не по IP):**

| Тип   | Имя (Host/Name)               | Значение (Value)     | TTL          |
|-------|--------------------------------|-----------------------|--------------|
| CNAME | `crm` (для `crm.company.com`) | `crm.lumiva.agency`  | 300 или Auto |

Дальше от клиента ничего не требуется — логотип, оформление, тариф, доступы и т.д. не меняются.
Просто просим написать нам, когда добавит запись (DNS обычно применяется от 5 минут до
нескольких часов, иногда — сутки, если у регистратора большой TTL по умолчанию).

Проверить самим, что DNS уже применился, можно на https://dnschecker.org (вбить домен клиента,
посмотреть, что везде отдаётся наш IP) — не обязательно ждать именно от клиента.

## С нашей стороны (пошагово)

### 1. Записать домен в pl1

Два места, где это можно сделать (оба пишут в одно и то же поле):

- **Список тенантов** (`pl1.lumiva.agency` → "Тенанты") → кнопка редактирования тенанта →
  открывается модалка "Редактирование тенанта" → поле **"Кастомный домен"** → вписать домен →
  **Сохранить**. Быстрый вариант, если уже открыт список.
- **Карточка тенанта** (клик по тенанту из списка → страница тенанта) → блок **"Кастомный
  домен"** в правой колонке → вписать домен → **Сохранить**. Тут же после провижининга будут
  кнопки "Отметить активным"/"Отметить ошибкой" — то есть для полного цикла в любом случае
  придётся зайти именно сюда.

После сохранения статус становится **pending**.

### 2. Проверить, что DNS уже указывает на сервер

```bash
dig +short <домен>
```

Пример:

```bash
$ dig +short crm.company.com
195.35.56.237
```

Если результат пустой или там другой IP — рано, DNS клиента ещё не применился, ждём/просим
проверить запись у него.

### 3. Выпустить сертификат и поднять vhost

На сервере (по SSH, из-под root):

```bash
/root/provision-tenant-domain.sh crm.company.com
```

Скрипт по шагам:
1. Ещё раз проверяет DNS (`dig`) — если домен не резолвится на этот сервер, останавливается
   с понятной ошибкой и не трогает certbot/nginx.
2. Выпускает Let's Encrypt сертификат: `certbot certonly --webroot -w /var/www/crm.lumiva.agency
   -d <домен>`.
3. Создаёт `/etc/nginx/sites-available/<домен>.conf` из шаблона
   `/etc/nginx/templates/tenant-domain.conf.template` — тот же билд SPA и тот же backend
   (`127.0.0.1:3000`), что у `crm.lumiva.agency`, плюс:
   - `location = / { return 302 /login; }` — клиент на своём домене не видит маркетинговую
     главную;
   - редирект маркетинговых/поддержки-страниц (`/blog`, `/pricing`, `/faq`, `/about`,
     `/solutions/*` и т.п.) на `https://crm.lumiva.agency` — на кастомном домене клиента
     остаётся только сама панель (логин + `/dashboard`, `/leads`, `/sales`, `/account/*` и
     остальные top-level роуты приложения), никакого дублирования маркетингового сайта.
4. Линкует конфиг в `sites-enabled`, проверяет (`nginx -t`) и релоадит nginx.

Успешное завершение выглядит так:

```
Done. https://crm.company.com is live and should redirect / to /login.
Now go to pl1 -> tenant -> Кастомный домен -> "Отметить активным".
```

**Если скрипт упал**, он печатает `FAILED: <причина>` и не трогает то, что уже было. Частые
причины:
- `Домен ... не резолвится` — DNS клиента ещё не применился, ждём и запускаем скрипт заново
  (безопасно запускать повторно).
- Ошибка certbot про rate limit (`too many certificates already issued`) — Let's Encrypt
  ограничивает выпуск сертификатов на один домен/неделю; если тестировали руками на этом же
  домене несколько раз подряд — придётся подождать. На реальных доменах клиентов это почти
  никогда не всплывает.
- `nginx -t упал` — где-то опечатка в домене или конфликт с уже существующим vhost'ом
  (например домен уже был кем-то занят руками) — смотрим текст ошибки, он прямо говорит, в
  какой строке проблема.

### 4. Отметить результат в pl1

Заходим в **карточку тенанта** (не в модалку из списка — кнопки активации только там), блок
"Кастомный домен":

- Скрипт завершился `Done.` → жмём **"Отметить активным"**. Статус → **active**, с этого
  момента `https://<домен>` реально резолвит тенанта на странице логина.
- Скрипт упал → вписываем причину в поле рядом и жмём **"Отметить ошибкой"** (статус →
  **failed**, текст ошибки виден в карточке всем, кто потом откроет тенанта). Поправляем
  проблему (обычно — ждём DNS) и повторяем шаг 3.

### 5. Проверить руками

Открыть `https://<домен>` в обычном браузере (лучше в приватном окне, чтобы не мешала старая
сессия):

- сертификат должен быть валидным (замочек, без предупреждений);
- сразу должен открыться экран логина (не главная страница lumiva.agency);
- поле "Company key" не должно быть видно — только email и пароль, домен уже подставляет
  тенанта автоматически (проверяется через `GET /v1/tenants/by-domain?host=<домен>`);
- после входа — обычный CRM, тот же тариф, тот же billing, ничего не отличается от входа
  через `crm.lumiva.agency`.

## Известный подводный камень: Expo dev-сервер и default_server

На сервере отдельно (не связано с CRM) крутится Expo dev-сервер мобильного приложения
(`/root/mobile`, процесс `expo start --lan`, слушает `:8081`). Его nginx-конфиг
`/etc/nginx/sites-available/metro` изначально был объявлен `default_server` на 80 порту —
то есть **любой** домен без своего явного vhost'а (в том числе новый клиентский домен на
этапе провижининга) вместо 404/ACME-challenge получал ответ от Expo. Это ломало выпуск
сертификата для любого нового домена (certbot получал JSON от Expo вместо challenge-файла).

Исправлено 2026-09-03: `default_server` убран у `metro`, вместо этого явно назначен
`crm.lumiva.agency.conf` (порт 80 у него и так уже правильно отдаёт `.well-known/acme-challenge/`
и редиректит остальное на https). Expo по-прежнему доступен напрямую на `:8081` — это не
затронуто, менялась только nginx-маршрутизация порта 80 для незнакомых доменов.

Если снова увидите в логе certbot ошибку про JSON/"exposdk" при выпуске сертификата на новый
домен — значит кто-то опять поставил `default_server` на посторонний vhost, ищите его через
`nginx -T | grep default_server`.

## На будущее

- **Продление сертификата** — ничего делать не нужно, общий `certbot.timer` на сервере
  продлевает все сертификаты автоматически, включая новые.
- **Один домен — один тенант**: бэкенд не даст привязать уже занятый домен к другому тенанту
  (вернёт ошибку "Этот домен уже используется другим тенантом").
- **Резолвинг работает только пока статус active** — если домен в `pending` или `failed`,
  `https://<домен>` физически ещё не поднят (нет ни vhost'а, ни сертификата), так что заходить
  туда рано в любом случае.
- **Отключить кастомный домен** — в pl1 (список или карточка) очистить поле и сохранить
  (статус → `none`, резолвинг по этому хосту перестаёт работать). Сам nginx-vhost и
  сертификат при этом **не удаляются автоматически** — это разовая ручная зачистка на
  сервере, если домен больше никогда не понадобится:
  ```bash
  rm /etc/nginx/sites-enabled/<домен>.conf /etc/nginx/sites-available/<домен>.conf
  systemctl reload nginx
  certbot delete --cert-name <домен>
  ```
