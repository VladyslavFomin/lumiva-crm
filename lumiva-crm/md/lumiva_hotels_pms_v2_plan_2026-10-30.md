# PMS v2 по ТЗ Hospitality Suite — выводы и план (2026-10-30)

Источник: `md/TZ_Lumiva_Hospitality_Suite_v2.md` (раздел 5 «PMS Core» + связанные 4, 18, 29) против текущего кода
`backend/src/hotels` и `frontend/src/pages/hotels`. Предыдущий план: `md/lumiva_hotels_pms_gap_plan_2026-10-25.md`.

## Выводы

1. **ТЗ описывает систему «с нуля»** (монорепозиторий, Prisma/Drizzle, RLS, outbox, BullMQ, uuid v7, `amount_minor`).
   Переписывать не будем: модуль «Отели» уже на NestJS + TypeORM + PostgreSQL, с данными живых клиентов (ATG).
   Берём **функциональные требования** и ID (`PMS-0xx`), реализуем в текущей архитектуре.
2. **Дизайн из ТЗ (раздел 22: индиго-токены, моушн-таблица) не берём** — решение владельца 2026-10-30, дизайн будет
   меняться. Новые экраны собираются в текущей дизайн-системе (`md/design-system.md`) — так их проще перекрасить потом.
3. **Сильные стороны уже есть** (из этапов 2026-07…10-25): партнёры, контракты, квоты/release, блоки, EB/SPO,
   питание, дети, комиссия/нетто, налоги (konaklama vergisi + KDV), журнал гостей KBS/МВД, скан паспорта (MRZ),
   доступность по типам (`/hotels/inventory` = PMS-015), выписки партнёрам, аналитика, онлайн-витрина.
4. **Главная дыра — ежедневная работа ресепшна.** Нет шахматки «номера × дни» с бронями (сейчас только красно-зелёная
   сетка по одному типу), нет переноса/переселения, no-show, walk-in, истории изменений брони, плана уборки,
   начислений в фолио, ночного аудита. Именно это делает PMS «продуктивной» — с этого и начинаем.
5. Ошибки бэкенда в модуле — русский текст. В новых эндпоинтах отдаём `code` и переводим на фронте (ru/en/tr).

## Этапы

### Этап 1 — Шахматка (Room Rack) + перенос + история  ← в работе
- `/hotels/rack`: строки — номера по типам, столбцы — 7/14/30/60 дней; полосы броней по статусу; иконки (дети, не
  оплачено, заметка, ранний/поздний, партнёр); строка «без номера» по каждому типу; подсветка «сегодня» и выходных;
  итог «свободно / загрузка %» по дням; фильтры (тип, статус номера), поиск по гостю/коду, навигация по датам.
- Наведение — карточка; клик — боковая панель (гость, даты, оплата, партнёр, история, действия: заселить, выселить,
  открыть бронь). Клик по пустой ячейке — новая бронь с подставленными отелем/типом/номером/датой.
- Перетаскивание полосы: на другой номер и/или даты (длительность сохраняется), из «без номера» — назначение номера,
  правый край — продление/сокращение. Проверка на сервере: занятость номера, доступность типа, статус брони.
  Конфликт → предложение поменять брони местами (E2E-15). Заселённого гостя — только переселение с причиной
  (старый номер → «грязный»). Цена за ночь сохраняется, итоги пересчитываются.
- История брони (PMS-028): все изменения пишутся по полям (было/стало, кто, когда); вкладка в карточке брони.
- Обновление шахматки опросом раз в 30 с и при возврате на вкладку.

### Этап 2 — Экран дня 2.0 и жизненный цикл брони
No-show (статус + массовая отметка), walk-in в один шаг, «в отеле» списком, прогресс дня, отмена с причиной и штрафом
по политике контракта, опционы с датой истечения и автоснятием (крон), бесплатные проживания с причиной + отчёт.

### Этап 3 — Housekeeping
Этаж/корпус у номера, OOO/OOS с периодом и причиной (видно в шахматке, держит номер), план уборки на день (выезды,
проживающие, заезды, приоритеты), распределение по горничным, мобильный экран горничной, проверка супервайзером,
Lost & Found.

### Этап 4 — Фолио
Начисления (проживание, питание, extras, минибар, ранний/поздний), сторно корректирующей строкой, несколько фолио на
бронь (гость / партнёр), кассовая смена, счёт с налогами из начислений.

### Этап 5 — Ночной аудит
Бизнес-дата отеля, проверки перед закрытием, автоначисление проживания, снимок дня, PDF-отчёт GM/финансам,
блокировка закрытых дней (`hotels_audit_override`).

### Этап 6 — Отчёты PMS
Occupancy/ADR/RevPAR по дням/месяцам/типам, прогноз on-the-books 30/90/365 с прошлым годом, pickup.

Каждый этап: бэкенд + фронт + ru/en/tr + проверка через API и браузер на тестовом отеле, тестовые данные удаляются.
