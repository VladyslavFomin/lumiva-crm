# Mobile ↔ Site: аудит полноты данных и план "не стыдно показать клиенту"

Дата: 2026-09-05
Статус: рабочий чек-лист для следующих раундов разработки (не блок-лог — тот остался в `MOBILE_APP_PLAN.md`)

## 0. Почему этот файл появился

Прошлый план (`MOBILE_APP_PLAN.md`) закрыл реальную боль (сломанные экраны, неверные URL, фейковые данные, недостижимые модули) — это было необходимо, но недостаточно: он не давал полноты **отображаемых данных**. Реальный вывод после первой живой проверки на устройстве: записи в БД есть (22 лида, 3 проекта, 4 контакта, 2 компании, 1 продажа, 4 товара, 1 бронирование у тестового тенанта) — но мобильные экраны показывают по каждой записи заметно меньше полей, вкладок и связанных данных, чем сайт. Отсюда ощущение "пусто", хотя данные есть.

Ниже — построчный аудит (сайт vs бэкенд vs мобильное приложение сейчас) по каждому модулю, плюс отдельно — сквозные проблемы, которые касаются всех модулей сразу (кастомные поля, валюта, история/комментарии, теги).

**Как читать таблицы:** ✅ уже показано в мобильном, 🔲 есть на сайте/бэкенде, но нет в мобильном (кандидат на добавление), ⛔ сознательно не переносим в мобилку (см. причину) — это НЕ "не дошли руки", это осознанное решение под мобильный форм-фактор.

## 1. Сквозные проблемы (касаются всех модулей)

### 1.1 Кастомные поля (Custom Fields) — самая крупная структурная дыра

На сайте есть общая система тенант-настраиваемых полей (`CustomFieldsManager`, типы text/number/email/phone/date/datetime/daterange/boolean/select/multiselect/textarea/url) для **Contact/Company/Lead/Sale/Project** — рендерится и в списке (как добавляемые колонки), и в детали (управляемая секция). Мобильное приложение сейчас **вообще не запрашивает и не показывает кастомные поля ни в одном модуле**. Учитывая, что часть реальных данных тенанта явно живёт именно там (например, паспорт/ID контакта на сайте прямо хранится в кастомных полях, а не в стандартных), это — то самое "невидимое" содержимое, из-за которого карточки выглядят пустыми, хотя данные внесены.

**Что нужно:** один переиспользуемый способ в мобильном API-слое — `fetchCustomFieldDefinitions(entityType)` + `fetchCustomFieldValues(entityType, entityId)` (эндпоинты подтвердить по `custom-fields` контроллеру бэкенда, вероятно `/custom-fields/:entityType` + значения приходят вместе с самой сущностью или отдельным вызовом — проверить на бэкенде перед реализацией), и один компонент `CustomFieldsSection` в библиотеке (`components/ui`), рендерящий значения по типу поля (текст/число/дата/чекбокс/select и т.д.), read-only на первом проходе (редактирование — второй итерацией). Подключить на деталях: Лид, Компания, Контакт, Проект, Продажа.

✅ **Сделано 2026-09-05.** По пути найден и исправлен **реальный, живой RBAC-баг на бэкенде**, который блокировал эту фичу полностью (и на сайте тоже, не только потенциально в мобильном): `GET /custom-fields` и `GET /custom-fields/entity/:entityType` были защищены `@RequirePermission('settings', 'read')`, а по дефолтной матрице прав `'settings'` есть только у ролей `owner`/`developer` — то есть `manager`/`sales`/`viewer`/`finance`/`support` (то есть большинство реальных пользователей CRM) не могли прочитать схему кастомных полей вообще, только словить 403/ошибку. Это ровно тот же класс бага, что уже несколько раз находили в этом проекте раньше (RBAC-гейт на чтение вместо гейта на запись/настройку). Значения самих полей (`entity.customFields`) при этом не были защищены отдельно — только их названия/типы через схему, так что дыра касалась именно "не видно подписей полей", а не самих данных.
Фикс: убрал `@RequirePermission('settings','read')` с трёх GET-хендлеров (`findAll`/`findByEntityType`/`findOne`) в `custom-fields.controller.ts` — чтение схемы теперь доступно любому аутентифицированному сотруднику (не требует specific permission), `POST`/`PATCH`/`DELETE` (создание/изменение/удаление самого поля) остались за `settings:write`/`settings:delete`, как и должно быть. Пересобран и перезапущен `lumiva_crm_api` докер-контейнер. Проверено на уровне кода (трассировка `RbacGuard.canActivate` — `if (!required) return true` при отсутствии декоратора), живой тест с не-owner аккаунтом в этой сессии не делал (нет под рукой таких учётных данных).

Мобильная реализация: `api/customFields.ts` (`fetchCustomFieldDefs(entityType)`, с in-memory кэшем на entityType — схема одна на тенанта, не нужно перезапрашивать с каждого экрана детали) + `components/ui/CustomFieldsSection.tsx` (read-only, форматирует значение по типу: select/multiselect резолвятся в `option.label`, date/datetime — `toLocaleDateString/String`, boolean — Да/Нет, email/phone/url — тапабельные строки с `Linking`). Подключено на всех 5 сущностях: Лид, Проект, Продажа, Контакт, Компания — везде рендерится в конце детали, только если для тенанта реально настроены активные поля этого типа (иначе секция не рендерится вообще, не показывает пустую рамку).

Не делали в этом заходе: редактирование значений (это read-only первый проход, как и планировалось), кастомные поля Продуктов (отдельный ACF-движок продуктов, не входит в общий `EntityType` enum — см. §5), `meta.source` (email/phone-поле может быть привязано к значению лида/компании вместо ручного ввода — не учитывали при рендере, не критично для просмотра).

Проекты/Продажи/Контакты/Компании/Бронирования на мобильном истории не показывают вообще, хотя у бэкенда есть реальные таблицы: `lead_activity`, `crm_project_activities`, `reservation_activity`, плюс общий audit log (`auditLog` в навигации сайта).

### 1.3 Комментарии / @упоминания

Проекты, Продажи, Контакты, Компании, Лиды — везде на сайте есть тред комментариев с упоминаниями сотрудников. В мобильном приложении комментариев нет ни в одном модуле (в детали лида есть кнопка "Добавить заметку/звонок" — она ведёт в никуда, дальше не реализована). Это отдельный кусок работы (нужен реальный эндпоинт комментариев + упоминания сотрудников), не выполняем "заодно" с историей — это разные API.

### 1.4 Теги

Лиды (через UTM), Проекты, Контакты, Компании, Продукты — у всех на сайте есть Tags (свободные текстовые теги, отображаются как чипы). Реализовано в мобильном только частично (Проекты/Продукты уже показывают `tags` в карточках/детали — это уже сделано корректно в этой сессии). Осталось: Контакты (в API `Contact.tags` уже есть и УЖЕ отображается в мобильном списке/детали — проверено, реализовано), Компании (аналогично уже есть). Статус этого пункта фактически ✅ — оставлен здесь для полноты аудита, доработки не требуется.

### 1.5 Валюта — реальная находка: сайт сам делает это криво, разбираться нужно осознанно

Аудит веб-кода показал: единого `formatCurrency()` на сайте **нет вообще**. Разные страницы дублируют одну и ту же логику по-разному:
- Большинство мест: `` `${amount.toLocaleString(locale)} ${currency}` `` — просто дописывают ISO-код валюты текстом (не через `Intl.NumberFormat(locale, {style:'currency'})`).
- В 4 файлах (`LeadsBoardPage`, `SalesAnalyticsPageV2`, `LeadsAnalyticsPageV2`) — захардкоженная функция символов **только на 4 валюты**: `TRY→₺, USD→$, RUB→₽, всё остальное→€` (то есть GBP и любая другая валюта на сайте покажет знак евро — это баг сайта, не наш).
- Модуль Продуктов вообще хардкодит `'ru-RU'` как locale независимо от языка интерфейса — во всех трёх местах отдельными копипастами одной функции.
- В Sales Analytics есть третий, самостоятельный механизм — режим конвертации валют с ручным вводом курса; в Маркетинге — четвёртый, независимый (localStorage) выбор "валюты отображения".

**Решение для мобильного** (осознанный выбор, не "исправить как получится"): сделать ОДИН правильный `formatMoney(amount, currencyCode, locale)` в `theme/` или `utils/` на базе `Intl.NumberFormat(locale, {style:'currency', currency})` с полной поддержкой ISO 4217 (не только 4 валюты) — это будет одновременно и правильнее, и проще в поддержке, чем повторять баг сайта. Единственное сознательное расхождение с сайтом: наш вариант покажет правильный символ для любой валюты (включая GBP), а не откатится на €, как сайт. Заносим в этот файл как задокументированное решение, чтобы не удивляться потом несовпадению с сайтом.

✅ **Сделано 2026-09-05**: `src/utils/money.ts` — `formatMoney(amount, currency)` на базе `Intl.NumberFormat('ru-RU', {style:'currency', currency})`, с fallback на `"${value} ${code}"` если Intl бросит на некорректный код. Подтверждено, что Hermes в RN 0.81 включает полный ICU/Intl из коробки — полифилл не нужен.

**Конкретные баги валюты, найденные в уже написанном мобильном коде:**
- ✅ `LeadsRoiScreen.tsx` — суммы показывались с захардкоженным `€` независимо от реальной валюты продажи. Исправлено: агрегация по лиду теперь хранит `currency` (валюту продаж этого лида), для сводных KPI-карточек (сумма по всем лидам сразу) берётся доминирующая валюта тенанта (у большинства тенантов она одна) — честный компромисс для агрегата по множеству записей, где в теории могут быть разные валюты.
- `api/products.ts` → `mapProduct()` — если `dto.currency` пустой, подставляется дефолт `'EUR'`; на практике у бэкенда `currency` всегда заполнено (`default: 'EUR'` на уровне БД), так что это не баг по факту — оставлено как есть.
- Остальные места (Sales list/detail, Projects list/detail, Products list/detail, Bookings) уже корректно берут валюту из самой записи (просто `toLocaleString` + код валюты, без `Intl.NumberFormat`) — по своей же инструкции этого файла НЕ трогали; при добавлении `formatMoney` в новые поля (Lead.amount, Project.amount, Booking price, Sale) везде использован новый форматтер для консистентности внутри новых блоков.

## 8. Дизайн — что значит "современнее", не расходясь с брендом сайта

Сайт сам по себе — намеренно минималистичный чёрно-белый Swiss-дизайн (см. §2 в `MOBILE_APP_PLAN.md`), это осознанный брендинг, не "недоделанность". Поэтому "современнее" здесь не должно означать "уйти от сайта в цветастый стиль" — а означает три конкретные вещи, которые сейчас объективно делают приложение суше самого сайта:

1. **Плотность информации на карточках/деталях** — сейчас мобильные карточки показывают 3-4 поля там, где на сайте их 8-12 (см. таблицы выше). Само по себе добавление полей из разделов 2-7 уже даст ощущение "полноценного продукта", а не только визуальная полировка.
2. **Настоящие фотографии вместо инициалов-аватаров везде, где они есть** — Продукты уже частично это делают (обложка товара); Контакты/Компании/Сотрудники на сайте, вероятно, тоже поддерживают `avatarUrl`/`logoUrl` — проверить и подключить реальные фото, а не только буквенные аватары, там где URL реально есть в данных.
3. **Глубина (elevation) и микро-детали** — сейчас все карточки на одном уровне плоскости (тонкая рамка + чуть заметная тень). Добавить лёгкую иерархию: hero-блоки на деталях (как уже сделано у Лида/Продукта) можно усилить залитым акцентным фоном/градиентом там, где сейчас плоский цвет; статус-пилюли — единообразный по всему приложению размер/паддинг (сверить, не разъехались ли в разных модулях за 12 блоков разработки).

Конкретно НЕ предлагается: смена шрифта, смена акцентного цвета, добавление ярких цветных иллюстраций — это разрушит визуальное соответствие сайту, которое было целью с самого начала плана.

## 14. Раунд 5 — вкладки Компании + найден и исправлен реальный баг маскировки данных, 2026-09-05

Реализуя "Контакты компании"/"Задачи компании" нашёл готовый эндпоинт `GET /companies/:id?withRelations=true`, который одним вызовом отдаёт `{company, contacts, leads, projects, tasks}` — дешевле, чем казалось по плану. Но по пути наткнулся на **третий реальный бэкенд-баг за сессию, на этот раз баг безопасности** (data-masking bypass, не RBAC-403 как первые два):

`CompaniesController.findOne()` при `withRelations=true` пропускал ВЕСЬ объект `{company, contacts, leads, projects, tasks}` через `maskOne(company as unknown as Company, ...)`, где `maskOne` реально ожидает саму `Company` (читает `.assignedUserId`, возвращает `{...company, phone: null, email: null}`). На форме `{company: {...}, contacts: [...], ...}` это давало два одновременных отказа:
1. **Фейл в опасную сторону (утечка):** для ролей с `contact_masking = 'always_mask'`/`'mask_until_assigned'` реальные `company.email`/`company.phone` (вложенные внутри `.company`) вообще не маскировались — только добавлялись бутафорские `phone: null, email: null` РЯДОМ на верхнем уровне объекта, не трогая настоящие поля. То есть контакты компании были видны ограниченным ролям ровно там, где сайт должен был их прятать.
2. **Фейл в безопасную сторону (но всё равно баг):** проверка `forceOwnOnly` (правило "видеть только свои записи") читала `company.assignedUserId`, которого на этой форме тоже нет (`undefined`) — значит для ролей с `foreign_records = 'hide'` любой вызов `withRelations=true` ловил 404 всегда, даже на собственных компаниях.

И это, и другое — баг возник из-за `as unknown as Company` typecast, который заглушил несовпадение типов вместо того, чтобы дать TS его поймать (тот же паттерн "type cast скрывает реальное несовпадение формы", что стоит иметь в виду при следующих находках).

Фикс: `findOne()` теперь при `withRelations=true` вызывает `findOneWithRelations()`, проверяет `forceOwnOnly` и маскирует именно `result.company` (не весь обёрнутый объект), возвращает `{...result, company: maskOne(result.company, ...)}`. Без каста — TypeScript теперь реально проверяет форму. Backend пересобран и перезапущен (третий раз за сессию).

Мобильная реализация: `fetchCompanyRelations(id)` (api/companies.ts) дергает тот же `withRelations=true` эндпоинт, вкладки "КОНТАКТЫ КОМПАНИИ"/"ЗАДАЧИ КОМПАНИИ" в `CompanyDetailScreen.tsx` (контакты — тап → `ContactDetail`, задачи — статус-пилюля/ответственный/срок, read-only).

Проверка: `npx tsc --noEmit` + `npx expo export --platform android` (5.02 МБ) — чисто. Живой тест fix'а маскировки с реальным ограниченным аккаунтом не делал (нет под рукой таких учётных данных в этой сессии, как и с первым RBAC-багом) — фикс проверен на уровне типов и логики (TypeScript теперь требует правильную форму без каста).

**Сразу же после фикса — предметно проверил, нет ли того же паттерна больше нигде** (`grep -rn "as unknown as" src --include="*.controller.ts"` по всему бэкенду, плюс `grep` на `maskOne`/`maskDetails`/`contactMaskingMode`): нашёлся **четвёртый реальный бэкенд-баг, идентичный третьему** — `ContactsController.findOne()` при `withRelations=true` страдал ровно тем же дефектом (та же форма `{contact, company, leads, projects}`, тот же `as unknown as Contact`), причём здесь маскировка серьёзнее — кроме `phone`/`email` есть ещё `DETAIL_FIELDS = ['address', 'customFields', 'meta', 'linkedin', 'website']`, которые тоже никогда не маскировались на этой форме. Исправлено тем же способом (`contacts.controller.ts`). Больше нигде в контроллерах такой маскировки нет (`maskOne`/`contactMaskingMode` существуют только в Companies и Contacts) — аудит закрыт, оба случая исправлены. Backend пересобран и перезапущен четвёртый раз за сессию.

Заодно, раз эндпоинт контактов теперь безопасен для `withRelations=true`, реализовал и оставшийся пункт таблицы Контактов — вкладки "Лиды контакта"/"Проекты контакта" (`fetchContactRelations()`, секция "СВЯЗАННЫЕ ЗАПИСИ" в `ContactDetailScreen.tsx`, тот же вызов заодно резолвит и имя компании — убрал отдельный `fetchCompany()`, теперь один запрос вместо двух).

## 16. Раунд 7 — реальная история для Sales/Contacts/Companies: план оказался неверным, нашлась готовая инфраструктура

Первоначальный план этого раздела (см. историю правок) предполагал строить с нуля три новые таблицы активности по образцу `crm_project_activities` — вывод §1.2 "у бэкенда НЕТ вообще эндпоинта/таблицы активности для этих трёх сущностей" был **неверным**: тот `grep` искал только `@Get(':id/activities')`/`history`-паттерны в самих модульных контроллерах и пропустил отдельный, уже подключённый модуль `src/audit-log/` — единый журнал `audit_logs` (entityType/entityId/action/summary/changes/actorName/createdAt), который **уже вызывается** из `SalesService.update()`, `ContactsService` (create/update/delete) и `CompaniesService` (create/update/delete) с содержательными русскими `summary`. Строить ничего не понадобилось.

Осталось решить одну проблему — тот же класс бага, что уже дважды чинил в этой сессии: `GET /audit-log` был **целиком** за `@RequirePermission('settings', 'read')`, то есть manager/sales/viewer/finance/support не могли увидеть историю даже своей же продажи/контакта/компании. Но здесь фикс тоньше, чем у custom-fields: этот эндпоинт — это ОДИН обработчик на два разных сценария:
1. Просмотр истории ОДНОЙ записи (`entityType`+`entityId`) — то же самое, что уже сделано для Leads/Bookings/Projects, не должно требовать `settings`.
2. Глобальная лента активности across весь тенант БЕЗ фильтра по записи — у неё нет вообще никакой ownership-проверки на уровне сервиса (`findGlobal` просто фильтрует по `tenantId`), то есть это по факту admin-обзорная возможность — её решил **оставить** за `settings`, как и было.

Фикс (`audit-log.controller.ts`): если `entityId`+`entityType` переданы — требуем базовое право модуля (`sales`/`contacts`/`companies`/`leads`/`projects`/`bookings`/`hotels`/`products`, через `RbacService.canForUser`, тот же метод что использует сам `RbacGuard`); если `entityId` не передан — по-прежнему `settings`. Это НЕ полная замена ownership-проверок (`foreign_records`/маскировка), которые есть у отдельных контроллеров сущностей — тот, кто уже открыл конкретную запись через её собственный `GET /sales/:id`(итд), где эти проверки применяются, получит доступ и к её истории; кто-то целенаправленно подбирающий чужие `entityId` напрямую через `/audit-log` теоретически может увидеть сводку изменений записи вне своей видимости — это осознанный компромисс по объёму, не идеальное решение, отмечаю явно, чтобы не забыть.

Мобильная реализация: `api/auditLog.ts` (`fetchAuditLog(entityType, entityId)`), новый переиспользуемый `components/ui/ActivityFeed.tsx` (4-й почти идентичный блок ленты активности за сессию — вынес в общий компонент, чтобы не копировать разметку в 6-й раз). Подключено сразу на всех трёх экранах (Sale/Contact/Company) — раз инфраструктура общая, не было смысла делать по одному модулю за раз, как планировалось изначально.

Backend пересобран и перезапущен **пятый раз** за сессию. Проверка: `npx tsc --noEmit` + `npx expo export --platform android` (5.04 МБ) — чисто.

## 17. Раунд 8 (план) — комментарии/@упоминания (§1.3)

Разведка веба (`LeadFormPage.tsx`, `src/pages/projects/mentions.ts`) показала, что механизм проще, чем можно было предположить:
- Формат комментария: `{id, author, createdAt, text, mentions?: string[], parentId?, likedBy?: string[]}` — плоский jsonb-массив прямо на сущности (не отдельная таблица/тред-сервис).
- `Lead.comments` и `Project.comments` (jsonb-колонки) **уже существуют** на бэкенде — у Sale/Contact/Company колонки нет вообще, нужно добавить.
- Упоминания — **не структурная фича**, а просто текст: пользователь печатает `@Полное Имя` или `@email` руками прямо в сообщении, `mentions[]` — это просто извлечённые regex'ом `@токены` для последующей подсветки. Автокомплита даже на сайте нет. Пуш/тост-уведомление упомянутому — тоже не реализовано на сайте (только визуальная подсветка). - Всё сохраняется через тот же generic `PATCH .../:id { comments: [...] }`, никакого отдельного comments-эндпоинта нет и на сайте — read-modify-write с фронта.

1. **Бэкенд**: одна миграция — `ALTER TABLE sales/contacts/companies ADD COLUMN comments jsonb`; добавить поле в `Sale`/`Contact`/`Company` entity + Create/Update DTO (по образцу `LeadCommentDto`). Пересборка/рестарт один раз в конце.

Автор/лайкающий — текущий пользователь через уже существующие `fetchProfile()` + `fetchStaff()` (резолв `staffUserId` по email, как на сайте: `currentStaffForComments?.id || profile.id`).
4. **Подключение на всех 5 деталях** — тот же `onUpdate`-паттерн, что и у `CustomFieldsSection` (компонент не завязан на конкретный API, родитель передаёт функцию сохранения).
