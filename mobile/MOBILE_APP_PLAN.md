# План пересборки мобильного приложения Lumiva CRM

Дата: 2026-09-05
Статус: план для поблочной реализации (Лиды → Проекты → Продажи → ...)

## 0. Планка качества

Предыдущая версия этого файла была правильной по фактам, но слишком узкой по амбиции — свелась к "заменить хардкод-цвета на токены". Это необходимое, но недостаточное условие. Цель — не портировать веб-страницы 1:1 в RN-компоненты, а сделать **нативное мобильное приложение 2026 года**, которое:

1. Использует тот же **визуальный ДНК**, что и сайт (чёрно-белый Swiss-minimal, Poppins, монохромные акценты, `lv-*` тулбар-язык, статусные пилюли) — это даёт узнаваемость бренда.
2. Но **не копирует десктопную структуру буквально**. То, что на сайте — hover-кнопка в таблице, на телефоне должно быть **swipe-действие по строке**. То, что на сайте — модалка по центру экрана, на телефоне — **bottom sheet снизу**. То, что на сайте — чекбоксы + плавающий бар, на телефоне — **long-press → режим выбора**. Раздел 3 фиксирует это соответствие явно, а не оставляет "как получится".
3. Выглядит и двигается как современное приложение, а не статичный набор вьюх: skeleton-загрузка вместо спиннера, spring-анимации при переходах и появлении карточек, haptic-отклик на действия, плавно скрывающийся при скролле хедер, а не мгновенная смена состояний.
4. Технически на это способна — а сейчас **не способна**, см. §1. Это первое, что чиним, до какого-либо экрана.

Ниже — расширенный план: техническая база → дизайн-система (полная, не только цвет) → структурные мобильные паттерны → библиотека компонентов → блоки по модулям с детальной раскладкой экранов/состояний/жестов, начиная с Лидов как эталонного блока.

## 1. Технический фундамент — чиним раньше любого экрана — ✅ сделано 2026-09-05

Обнаружено при аудите: `metro.config.js` **подменяет `react-native-reanimated` на пустышку** ([reanimated-stub.js](mobile/reanimated-stub.js)) с комментарием "prevents Reanimated v4 from initializing NativeWorklets in Expo Go where the native worklets module is incompatible". То есть весь пакет анимаций/жестов, ради которого он вообще стоит в зависимостях (`react-native-reanimated`, `react-native-worklets`, `react-native-gesture-handler`), **сейчас физически отключён**, потому что проект запускается через голый **Expo Go** (`npm start --tunnel`).

Следствие: без исправления любые "красивые современные анимации" в плане — это фикция, они не запустятся. Reanimated нужен именно для swipe-to-action по строкам, bottom sheet с физикой, collapsing header, плавных transition между списком/канбаном.

**Решение**, благо база уже подготовлена: в `package.json` уже есть `expo-dev-client`, а в `eas.json` уже описан профиль `development` (`developmentClient: true`). Значит переход изначально планировался, но не был доведён до конца.

Шаги (делаются один раз, до Блока 1):
1. Убрать подмену в `metro.config.js` (снести `resolveRequest`-хак и `reanimated-stub.js`).
2. Собрать dev-client через `eas build --profile development --platform android` (и `ios` при наличии Apple-аккаунта) — это нативная сборка с реальным Reanimated/Worklets, устанавливается на тестовое устройство/эмулятор один раз.
3. Дальше в разработке — `expo start --dev-client` вместо `expo start --tunnel` (Expo Go). Скрипты `package.json` (`android`/`ios`) обновить соответственно.
4. Проверить, что `react-native-gesture-handler` и `react-native-reanimated` реально инициализируются (лог без warning про worklets) — только после этого приступать к жестовым/анимационным компонентам из §3.

Если по любой причине EAS-сборка недоступна прямо сейчас (нет Apple-аккаунта, нет доступа к EAS) — временный fallback: анимации на `Animated` API из React Native (JS-driven, без Reanimated), это хуже по плавности на тяжёлых списках, но не блокирует остальную работу. Явно фиксируем в статусе блока, если работаем на fallback, чтобы потом вернуться и проапгрейдить.

**Что нашли и починили по пути** (все — реальные баги окружения, не гипотетические):
- `@reduxjs/toolkit` в зависимостях нигде не использовался в коде и конфликтовал по peer-зависимостям с React 19 — убран.
- `react-native-worklets-core` — вторая, неиспользуемая реализация воркетов, конкурирующая с нужным Reanimated 4 пакетом `react-native-worklets` — убран.
- `.pm2/` не было в корневом `.gitignore` (в отличие от всех остальных tool-cache директорий) — из-за этого `eas build` пытался упаковать живой сокет боевого процесс-менеджера и падал. Добавлено.
- `tsconfig.json` жёстко переопределял `moduleResolution` на устаревший `"node"`, конфликтуя с `customConditions` из `expo/tsconfig.base` (там уже правильный `"bundler"`) — из-за этого `tsc --noEmit`/`npm run typecheck` не запускались вообще. Убрано переопределение.
- Собран и провалидирован рабочий dev-client APK: https://expo.dev/artifacts/eas/TZHl7-nOV5bvCS5ga0R-N9SSJ6n8q1YBrlpfBwihrpE.apk — установить один раз на тестовое устройство, дальше `npm start` использует его вместо Expo Go.

### 2.2 Типографика

Сайт: **Poppins** 400/500/600/700 как основной шрифт, **JetBrains Mono** 400/500/600 — только для чисел/кодов/бейджей (это осознанный приём: моно-шрифт для данных создаёт "дашбордный", а не "текстовый" вид).

Шкала размеров, которую фактически использует сайт (собрать в `theme/typography.ts`):

| Роль | Размер / вес | Где |
|---|---|---|
| Page title | 20px / 600 | `.page-title` |
| Section title | 16px / 700 | `.sectionTitle` |
| Body | 14px / 400-500 | таблицы, карточки |
| Toolbar / meta | 12-12.5px / 400-500 | `.lv-tb-btn`, `.lv-view-tab` |
| Micro / badge | 10-11px / 600, uppercase, tracking-wide | `.badge`, `.pillTxt` |
| Числа (mono) | соответствует контексту, `JetBrains Mono` | KPI, счётчики, даты, ID |

Мобильная шкала должна быть немного крупнее эквивалентных ролей сайта (десктоп читают с 60см, телефон — с 30см, но пальцем тычут, а не мышкой — компромисс: не увеличивать бездумно до iOS Large Title 34px, как было в старом скелете, а держать 22-26px для заголовка экрана, это уже "не 2010" за счёт веса/трекинга, а не размера).

### 2.3 Форма и пространство

- Радиусы: `6 / 8 / 10 / 12 / 16 / 20` px — те же ступени, что на сайте (`radius-sm...xl`), плюс `999` для пилюль/аватаров.
- Отступы — 4pt grid (`4/8/12/16/20/24/32`), не рандомные числа как в текущем скелете (`paddingHorizontal: 9, paddingVertical: 4` и подобное — привести к сетке).
- Тени: 3 уровня, переиспользовать формулы сайта, адаптировать под RN `shadow*`/`elevation`:
  - `card` — едва заметная (для строк списка, мелких карточек);
  - `card-md` — карточки дашборда/KPI, модальные листы;
  - `btn-primary` — только под primary-кнопкой/FAB (`0 4px 12px rgba(34,34,34,0.25)`).
- **Тёмная тема не рисуется тенями** (на чёрном фоне box-shadow не читается) — вместо этого элевация через **послойную яркость поверхности** (surface tinting, как в Material 3 / iOS): `background` → `surface` (+2% яркости) → `surfaceVariant`/`cardElevated` (+4-6%) → чем "выше" элемент, тем светлее его подложка. Это уже частично заложено в `darkColors` (`card: #1C1C1E`, `cardElevated: #2C2C2E`) — оставляем и достраиваем на все компоненты.

### 2.4 Кнопки и статус-элементы

- `.btn-primary` — чёрный/белый (инверсия в dark), **UPPERCASE, полужирный, tracking-wide**, `radius 10`, тень `btn-primary`.
- `.btn-secondary` / `.btn-ghost` / `.btn-danger` / `.btn-icon` — см. предыдущую версию плана, без изменений по сути.
- `.lv-tb-btn` (тулбар-кнопка списков) — `padding 7×10`, рамка `line-2`, `radius 8`, `12.5px`; `.active` — заливка `ink`.
- `.lv-view-tab` — подчёркивание вместо капсул для переключения видов.
- `.lv-bulk-bar` — плавающая чёрная панель при мультивыборе, полупрозрачные кнопки, danger-кнопка краснеет.

### 2.5 Иконография

Сайт использует простые line-иконки (SVG, ~18-20px, `stroke-width 1.5-2`). В мобилке уже стоит `@expo/vector-icons` (Ionicons) — **не менять библиотеку**, но зафиксировать правило вместо текущего "как получится":
- Размерная шкала: `16` (инлайн в тексте/бейдже) / `20` (тулбар/список) / `24` (таб-бар/хедер) / `28-32` (пустые состояния, некликабельно).
- Состояние active/inactive — не через смену размера, а `outline` → `filled` вариант той же иконки (уже так частично сделано в `AppNavigator.tsx` для таб-бара — распространить на все переключаемые иконки: избранное, чекбоксы, свернуть/развернуть).
- Цвет иконки всегда из `colors.*`, никогда захардкожен.

### 2.6 Моушн (новое — на сайте это неприменимо, определяем с нуля под нативное приложение)

Единая моушн-система, чтобы приложение не выглядело "механическим":

| Контекст | Тип анимации | Параметры |
|---|---|---|
| Появление карточек списка (первая загрузка) | fade + slide-up, с небольшим stagger (~30ms между карточками, максимум на первые 8-10) | `duration 220ms`, `ease-out` |
| Переход между экранами стека | нативный platform-default (iOS: push с полупрозрачным затемнением предыдущего, Android: material shared-axis) | штатный `@react-navigation/native-stack` |
| Открытие bottom sheet / модалки | spring снизу + затемнение фона | `damping ~18-20, stiffness ~180` (Reanimated spring) |
| Swipe-действие по строке | подхватывает палец 1:1 (interactive gesture-driven), не "анимация по кнопке" | `react-native-gesture-handler` + `Reanimated` shared value |
| Нажатие кнопки/карточки | `scale 0.97` + едва заметное затемнение | `duration 100ms` |
| Смена таба/сегмента | пилюля/подчёркивание "едет" к новой позиции, а не телепортируется | Reanimated `withSpring` по layout |
| Pull-to-refresh | кастомный индикатор в стиле бренда (не системный серый спиннер), лёгкая haptic-вибрация в момент триггера | `expo-haptics` (добавить в зависимости) |
| Успех действия (лид создан, сделка закрыта) | короткий Lottie-конфетти/чек **только** для явно "празднуемых" событий (не на каждый чих) | переиспользовать `success-check.json` / `confetti-burst.json` — они уже нарисованы для веба, см. §2.7 |

Правило: анимация всегда либо даёт обратную связь (что-то произошло), либо ориентирует (откуда/куда переместился контент) — никогда не декоративная ради декоративности.

### 2.7 Переиспользуемые Lottie-ассеты

В веб-репозитории уже существует библиотека Lottie-анимаций (`lumiva-crm/frontend/src/assets/lottie/*.json`: `success-check`, `confetti-burst`, `approval-stamp`, `data-extraction`, `sales-funnel` и др., см. память "Lottie animations initiative" — 21/30 уже подключены на сайте к пустым/загрузочным состояниям). Для мобилки:
- Подключить `lottie-react-native` (проверить совместимость с dev-client сборкой из §1).
- **Не рисовать новые анимации с нуля** — скопировать те же `.json` в `mobile/assets/lottie/` и переиспользовать 1:1 (это тот же бренд-язык, плюс экономия времени).
- Использовать для: пустых состояний списков (вместо серой иконки-заглушки), success-подтверждений, длинных загрузок с понятным ожиданием (импорт CSV и т.п.).

## 3. Мобильные структурные паттерны — где НЕ копируем сайт 1:1

Ключевой ответ на "делаем как на сайте, но более структурировано т.к. приложение": ниже — таблица прямого соответствия "паттерн сайта → паттерн приложения", чтобы при реализации каждого блока не изобретать заново.

| На сайте (desktop) | В приложении (mobile) | Почему |
|---|---|---|
| Hover-кнопки действий в строке таблицы | **Swipe-действия** по строке (влево — архив/удалить, вправо — быстрое действие: позвонить/написать) + long-press → контекстное меню | На тачскрине нет hover; свайп — нативный жест, которым уже пользуется каждый |
| Чекбоксы в каждой строке + `lv-bulk-bar` снизу при выборе | **Long-press на строке** входит в "режим выбора" (чекбоксы появляются анимированно), тот же `BulkActionBar` снизу, но с safe-area отступом и haptic при входе в режим | Чекбоксы по умолчанию на мобильном списке — лишний визуальный шум на 90% времени |
| Модальное окно по центру (`.modal-overlay/.modal-panel`) | **Bottom sheet** (частичная высота с "ручкой" сверху, drag-to-dismiss) для форм/фильтров/деталей; **полноэкранный модальный стек** только для многошаговых мастеров (создание сделки с позициями и т.п.) | Bottom sheet — стандарт нативных приложений, легче закрыть жестом |
| Таблица с горизонтальным скроллом и множеством колонок | **Карточный список** (2-3 ключевых поля + статус-пилюля + аватар), остальные поля — на детальном экране; опционально плотный "табличный" режим-переключатель для power-юзеров | Таблица с 8 колонками нечитаема на 380px ширины |
| Левый сайдбар с деревом навигации (все 20+ модулей) | **Нижний таб-бар** (5 самых частых модулей) + экран "Ещё" (сетка/список всех остальных модулей, сгруппированных как в сайдбаре сайта) + поиск по разделам | На телефоне нет места для постоянного дерева на 20+ пунктов |
| `.lv-view-tab` переключение Список/Канбан/Календарь через горизонтальные табы над таблицей | Те же табы, но канбан на телефоне — **горизontally-swipeable колонки** (одна колонка на экран + свайп между статусами), а не уменьшенная копия десктопной доски | Полная канбан-доска с 5-6 колонками физически не помещается на телефон |
| Инлайн-редактирование ячейки таблицы (клик по ячейке → инпут) | Тап по полю на детальном экране → **bottom sheet редактирования этого поля** | Инлайн-редактирование в маленькой ячейке пальцем неточное |
| Фильтры — попап рядом с кнопкой | **Bottom sheet "Фильтры"** на всю доступную высоту с секциями и кнопкой "Показать N результатов" внизу | Стандартный мобильный паттерн (Ozon/Avito/любой шоппинг-апп), пользователю не нужно объяснять |
| Раскрывающиеся вложенные группы в списке (`lv-group-toggle`) | Те же collapsible-группы, но с более крупной тач-зоной заголовка (44pt минимум) | Accessibility/Fitts's law на тач-интерфейсе |
| Header остаётся на месте при скролле таблицы | **Collapsing header**: крупный заголовок сворачивается в компактный при скролле вниз, панель поиска/табов "прилипает" (sticky) | Экономит вертикальное место на маленьком экране, при этом ощущается "живым" |
| Drag&drop конструктор автоматизаций (полноценный canvas) | На старте — **только просмотр + вкл/выкл шага + быстрое редактирование параметров**, полноценный визуальный конструктор — не в мобильном MVP | Canvas-редактор жестами на телефоне — отдельный большой продукт, не нужен в первой версии |

## 6l. Найдено при первой реальной проверке на устройстве (2026-09-05) — вход с 2FA был невозможен

Не баг конкретного блока, а блокирующая проблема самого входа, всплывшая только при живом тестировании на реальном аккаунте владельца. `LoginScreen`/`api/auth.ts` никогда не проверяли `twoFactorRequired` в ответе `/auth/login` — при включённой 2FA бэкенд возвращает `{twoFactorRequired: true, challengeToken}` без `accessToken` вообще, а мобильный код безусловно пытался сохранить `accessToken` в `AsyncStorage`, получал `undefined` и падал с "[AsyncStorage] Passing null/undefined as value is not supported". То есть **аккаунты с включённой 2FA не могли залогиниться в приложение в принципе**, с самого начала — вне зависимости от того, насколько верны email/пароль/ключ клиента (что и сбивало с толку: сообщение "Invalid credentials" на самом деле было настоящей ошибкой неверного пароля с одной из первых попыток, а не тем же багом).

Добавлен второй экран — ввод 6-значного кода/резервного кода (`POST /auth/verify-2fa`), с возвратом к обычному входу. Заодно починена декоративная ссылка «Забыли пароль?» (была голым `<Text>` без `onPress`) — теперь реально дёргает `POST /auth/request-reset`, и убрана ещё одна фейковая версия приложения в футере экрана логина ("CRM 4.12" → реальная `app.config.js` версия).

**Диагностика заняла отдельный заход**: проверил напрямую в БД тенанта (`docker exec` в `lumiva_crm_db`) реальный `clientKey` ("admin" — оказался верным, не выдумкой пользователя) и `twoFactorEnabled` флаг пользователя, прежде чем чинить — не гадал по одному сообщению об ошибке, которое бэкенд намеренно не различает между "нет такого email" и "неверный пароль".

**Отдельно обнаружено при той же сессии живого тестирования**: dev-режим через Metro-туннель (`exp.direct`) оказался ненадёжным для этого проекта — дев-бандл весит ~11.6 МБ и на реальной мобильной сети через туннель регулярно не догружался ("Unable to load script", зависания ANR). Решение — гонять проверки через отдельно собираемый `eas build --profile preview` (автономный APK со встроенным JS, без Metro/туннеля вообще) вместо `--profile development` + live-туннеля. Держим это как стандартный способ проверки на реальном устройстве для этого проекта дальше.

## 6m. Логаут падал при выходе из аккаунта (2026-09-05)

`ProfileScreen` дёргал `navigation.getParent()?.getParent()?.reset({ routes: [{ name: 'Auth' }] })` — рабочий способ только если экран `Auth` реально примонтирован в навигаторе в этот момент. У нас `AppNavigator` держит `isAuthed` в state и **условно** рендерит либо экран `Auth`, либо всё авторизованное дерево — то есть пока `isAuthed === true`, роута `Auth` физически не существует, и `reset` тихо проваливался (кнопка "Выйти" ничего не делала).

Исправлено через нормальный React Context вместо пробивания трёх уровней `getParent()`: новый `src/auth/AuthContext.tsx` с единственным методом `logout()`, `AppNavigator` оборачивает дерево в `<AuthProvider logout={...}>` и сам меняет `isAuthed`, `ProfileScreen` просто вызывает `useAuth().logout()`. Заодно это правильный паттерн для любого будущего экрана, которому понадобится дёрнуть логаут — не нужно протаскивать `navigation` через пропсы.

## 6p. Аудит drag-and-drop механики сайт↔приложение (2026-09-05)

По второй части жалобы пользователя ("в самой механике, драг энд дропах... не так, что будто бы два разных приложения") — прошёлся по всем `draggable`/`onDragStart` местам на сайте (`grep` по `lumiva-crm/frontend/src`), чтобы понять, где десктопный drag реально нужно чем-то заменить на мобильном, а где расхождение уже осознанно (см. таблицу §3 этого файла).

Найдено 4 категории:
1. **Канбан-доски** (`LeadsBoardPage`, аналогично ожидался бы у Проектов/Задач компаний) — на мобильном канбане Лидов уже принято осознанное решение НЕ копировать десктопный drag между колонками (§3, строка 5: колонки не помещаются side-by-side на экране телефона, там свайп-пейджинг одна колонка на экран). Но при этом сам компонент карточки **функционально был урезан**: единственный способ сменить статус — кнопка-стрелка "вперёд", которая двигала только на один шаг по фиксированной цепочке (`new→in_progress→waiting→won`) и не давала вернуть назад или отметить "Проиграно" из произвольной колонки — то есть даже без литерального drag не было паритета возможностей с сайтом (там можно перетащить в любую колонку). **Исправлено**: `LeadsKanbanScreen.tsx` — long-press по карточке (плюс явная кнопка-иконка `swap-horizontal`) открывает bottom sheet со списком всех статусов, тап по любому — мгновенный переход. Это стандартный мобильный паттерн замены drag (как в Linear/Trello mobile), сохраняющий полную функциональность сайта без буквального перетаскивания пальцем.
2. **Reorder внутри произвольной "кастомной группы" в списке Лидов** (`LeadsListPage.tsx`, `groupMode === 'custom'`) — ручная сортировка лидов при кастомной группировке списка. В мобильном приложении режима "кастомная группировка" списка нет вообще (сайт-специфичная power-user фича таблицы) — сознательно не переносим, низкий приоритет и малый охват пользователей.
3. **Задачи проекта** (`ProjectTasksPage.tsx`, `draggable={editable}` на строке задачи — reorder/nesting задач) — при проверке оказалось, что в мобильном приложении **вкладки задач проекта нет вообще** (`ProjectDetailScreen.tsx` не запрашивает и не показывает задачи ни в каком виде). Это не вопрос "жест против тапа" — это отсутствующая фича целиком, уже зафиксированная в `MOBILE_DATA_PARITY_PLAN.md` §3 как "крупный кусок, начать с read-only списка" — drag-reorder имеет смысл обсуждать только после того, как появится сам список задач.
4. **Дашборд-виджеты** (`DashboardWidgetChrome.tsx`, drag для перестановки виджетов на кастомном дашборде) — на мобильном дашборд с фиксированной раскладкой, кастомизация раскладки — desktop-специфичная опция для power-юзера, не приоритет для витрины на телефоне.

**Вывод**: единственный реальный, стоящий фикса разрыв в drag-механике был найден и закрыт (канбан-статусы п.1) — остальное либо уже сознательно другое по архитектуре (мобильный канбан), либо упирается в отсутствующую фичу целиком (задачи проекта — см. план ниже), а не в способ ввода.

## 9. Импорт нового дизайна «Liquid Glass» (claude.ai/design проект `lumiva`, файл `mobile-app-screens.html`) — план, зафиксирован 2026-09-08

- Градиентные цветные "ауры" на фоне экрана (`radial-gradient` в oklch), разные для light/dark.
- Единый набор примитивов, которого сейчас нет: `Chip`/`Seg`(сегмент-контрол)/`Sheet`(шторка снизу, переосмысленная), `Fld`/`Inp`/`Area`/`Pick`(чипы-выбор)/`Tog`(свитч-строка), `Spark`(мини-график), `KV`(строка ключ-значение), `AvStack`(стопка аватаров), availability-грид, месячный календарь, чат-бабблы, кастомный DnD-движок на pointer-событиях (long-press → поднять → drop в любой список, с авто-скроллом краёв) — используется в канбанах и в конструкторе кастомных полей.
- Общий кастомный набор SVG-иконок (`I.*`, Lucide-style, stroke 1.6) вместо `@expo/vector-icons` — **отдельное решение**, см. §9.1.

Это не "докрасить экран" — это второй капитальный пересмотр всего мобильного приложения после §1-§8. Ниже — план без начала реализации (зафиксирован по явной просьбе пользователя: сначала разбивка на пункты).

### 9.1 Этап 0 — фундамент новой дизайн-системы (обязателен до любого экрана)

Часть — прямой реcкин существующих компонентов из §4 (`StatusPill`→ужe есть аналог `mg-pill`, `Skeleton`→`mg-skel` и т.д.), часть — с нуля.

**Развилка, которую нужно решить с пользователем перед стартом**: делаем ли реcкин **инкрементально** (новая и старая дизайн-система сосуществуют экран-за-экраном, дольше по времени жить с двумя стилями одновременно) или **одним заходом на модуль** (весь модуль разом, короче переходный период, но крупнее один PR)? ## 9.7 Найденный при реcкине пробел в Маркетинге — реально почи́нен (2026-09-08)

Пользователь спросил про находку из §9.5 ("`ChannelDetailScreen` — полностью бутафорский экран"). При проверке нашлось **больше, чем изначально зафиксировал фоновый агент** — это не только фейковые данные на одном экране, а реальный, ранее не замеченный баг данных, живущий в проде прямо сейчас:

Секции "Активные кампании" и "Подключение" (Ad Account ID, OAuth-токен) удалены целиком — реального источника данных для них нет: `GET /marketing/campaigns` на бэкенде — сознательный статический стаб, всегда возвращает `[]` (комментарий в коде: "кампании в CRM пока ведутся иначе"), а Ad Account ID/OAuth-статус были просто выдуманы, не связаны ни с каким реальным интеграционным модулем (Meta/Google Ads интеграции реально существуют на бэкенде — `integrations/meta-ads`, `integrations/google-ads` — но связка "канал трафика ↔ конкретная интеграция" отдельная задача, не делал наугад).
